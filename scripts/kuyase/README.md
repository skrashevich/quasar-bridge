# E2E-проверка Bridge в КУЯСЭ

Workflow `.github/workflows/kuyase.yml` запускается на push, pull request,
вручную через Actions → station emulator → Run workflow и через `workflow_call`.
Секреты не нужны: все внешние сервисы заменены локальными HTTP/WebSocket
фикстурами внутри гостевой системы. Проверяется настоящий standalone-пакет
Bridge, собранный из текущего checkout, в настоящей прошивке станции.

## Матрица

| Прошивка | Профиль КУЯСЭ | Пакеты Bridge | Запуск |
| --- | --- | --- | --- |
| Mini 1 | `yandexmini` | ARM64, ARMv7 | Всегда |
| Станция 2 | `station2` | ARM64, ARMv7 | Всегда |
| Лайт 1 (YNDX-00025) | `yandexmicro` | ARM64, ARMv7 | PR, push в `main`, вручную |
| Mini 2 без часов (YNDX-00020) | `yandexmini2nc` | ARM64, ARMv7 | PR, push в `main`, вручную |
| Миди (YNDX-00054) | `cucumber` | ARM64, ARMv7 | PR, push в `main`, вручную |

На PR, при push в `main` и при ручном запуске выполняются десять проверок.
При push в другие ветки и через `workflow_call` проверяются только Mini 1 и
Станция 2 на обеих архитектурах. Для каждого сочетания прошивки и архитектуры
запускается отдельное задание с отдельной VM. При сбое одного задания
`fail-fast: false` позволяет завершить остальные. В GitHub Actions Summary
шага планирования перечислены запланированные и исключённые профили.

Для Лайт 1, Mini 2 без часов и Миди используется по одной OTA из
[закреплённой ревизии каталога](https://huggingface.co/datasets/vypivshiy/iot-quasar-dataset/commit/8a027abcba7920a570192cf38c9689f344de66f0).
Для Mini 1 и Станции 2 используются OTA Яндекса. Версии и контрольные суммы
зафиксированы в `firmware.py`. Метка `yandexmidi` в каталоге обозначает
прошивки Станции 2, а не Миди.

У `yandexstation` (Станция 1), `elari_a98`, `jbl_link_music`,
`jbl_link_portable`, `lightcomm`, `linkplay_a98`, `prestigio_smart_mate` из
этой ревизии датасета нет подтверждённого профиля в закреплённом КУЯСЭ.
Данные для Mini 2 с часами, Лайт 2 и других отсутствующих моделей не
подменяются похожей OTA. Покрытие не означает, что физические устройства проверены.

## Сценарии в каждой VM

| Сценарий | Проверяемое поведение |
| --- | --- |
| `config` | Standalone-бинарник принимает конфигурацию (`-check-config`) |
| `health` | Работает `/healthz`, включён hybrid и доступен AirPlay |
| `weather`, `music`, `timer` | VoiceInput → ASR → разрешение облачного запроса → ответ Яндекса; LLM и HA не вызываются |
| `llm` | VoiceInput → ASR → HTTP Chat Completions → ответ Bridge и запрос синтеза TTS |
| `llm_urls` | Ответ модели со ссылкой на источник: URL и Markdown отсутствуют в речи и запросе TTS, исходная ссылка сохранена в карточке и HTTP API истории |
| `text` | TextInput → LLM → ответ и TTS без ASR |
| `dialogue` | После закрытия WebSocket и переподключения LLM получает предыдущие вопрос и ответ |
| `isolation` | Другая колонка не получает чужой контекст |
| `reset` | Сброс диалога не вызывает LLM, следующий вопрос приходит без старой истории |
| `home` | MCP inventory/exposure → план LLM → ровно один service call → подтверждение состояния; вопрос о состоянии не выполняет действий |
| `failure` | HTTP 503 от LLM даёт понятный ответ; следующий запрос того же устройства проходит без ошибочного контекста |
| `start`, `stop` | Голосовое включение/выключение настоящего AirPlay-приёмника; состояние сохраняется после закрытия WebSocket |
| `web-overview` | На главной видны режим, модель нейросети и данные колонки из статуса Bridge. Выбор темы сохраняется при перезагрузке |
| `web-routing` | Создание и редактирование правила, проверка совпадения прямо в редакторе, применение, выбор обработчика и удаление правила |
| `web-settings` | Поиск настройки, сохранение в файл, применение без перезапуска и возврат прежнего значения |
| `web-chat` | Две реплики через локальную LLM с проверкой контекста, восстановление переписки после обновления страницы и новый диалог |
| `web-history` | Мобильный поиск по журналу голосового сценария `llm_urls`, вопрос и ответ отдельными репликами, ссылка источника и пустая выдача |
| `web-airplay`, `web-logs` | Кнопки включают и останавливают приёмник. Журнал показывает события, поддерживает паузу, поиск и скачивание |
| `web-account`, `web-models` | Отмена входа через OAuth с возвратом в панель. Для тестовой подписки — загрузка видимых моделей, выбор из списка и проверка сохранённой и активной модели |
| `web-access` | Защитные HTTP-заголовки, отказ на GET для действий и отклонение межсайтовых запросов и POST с неверным типом содержимого |
| `airplay-cleanup` | Приёмник остановлен, процессов `station-pcm` не осталось |
| `shutdown` | Процесс Bridge завершился и PID больше не существует |

Для каждого запроса контроллер проверяет точный ответ, связь ответа с исходным
request ID, неизменность ASR и число обращений к каждому бэкенду. Локальный
обработчик Яндекса возвращает ответ только после `ContinueRequest`: обход
ожидания разрешения или отправка локальной команды в облако приводят к ошибке.
Фикстура LLM проверяет сообщения истории, а MCP хранит изменяемое состояние
света и проверяет цель команды. Неожиданные HTTP/MCP/протокольные запросы
завершают проверку ошибкой. Классификатор выключен для воспроизводимости:
проверяются штатные правила и контекст диалога.

В `llm_urls` используется пример ответа о матче «Баварии» со ссылкой
`[app.fcbayern.com](https://app.fcbayern.com/en/?utm_source=openai)`.
Проверяется фактический текст `TtsGenerate`, а не только наличие вызова TTS.
Запись журнала включена только для синтетических диалогов этого стенда;
история проверяется через `/diagnostics/api/history` работающего Bridge.
Сценарий запускается в каждом выбранном сочетании прошивки и архитектуры
и отдельно отражается в JSON, JUnit и GitHub Actions Summary.

Chromium на хосте открывает панель гостевой системы через временный проброс
`adb forward`. Каждый веб-сценарий получает отдельный профиль браузера.
В `web-account` Playwright показывает тестовую страницу согласия, а возврат
обрабатывает Bridge. Для `web-models` в том же снимке VM запускается второй
экземпляр пакета с синтетической подпиской и локальным HTTPS-каталогом.
Тестовый сертификат доверен только этому процессу. Учётная запись OpenAI
для запуска не требуется. При сбое браузерного сценария в артефакт попадают
лог ошибки и снимок страницы, если Chromium успел её открыть.

Ошибка сценария не мешает остальным сценариям той же VM; ошибка запуска или
инфраструктуры завершает job. В обоих случаях workflow возвращает ошибку.
После завершения доступны:

- таблица сценариев и длительности в GitHub Actions Summary;
- `result.json` и `junit.xml` с результатами отдельных сценариев;
- логи Bridge, локальных бэкендов, гостевой системы, VM и QEMU;
- журнал синтетических диалогов для проверки исходного текста и озвучки;
- при сбое подготовки — `prepare.log`.

Артефакты `kuyase-<board>-<arch>-logs` хранятся 7 дней. Длительности служат
диагностикой; автоматический поиск регрессий здесь основан на проверках
поведения, без сравнения скорости разных shared runners.

## Эмулятор и прошивки

Используется Ubuntu 24.04 и QEMU с программной эмуляцией ARM.
`ipxe-qemu` предоставляет `efi-virtio.rom` для `virtio-net-pci`.
КУЯСЭ 1.5.0 собирается из закреплённого коммита на runner с
`--no-default-features`: это headless-сборка без GUI и оконных библиотек.
CLI собирается один раз для всей матрицы под libc runner. Гостевое ядро
и ARM-мост берутся из закреплённого `kuyase-headless-linux64.tar.gz` 1.5.0.
Исходники, гостевое ядро/мост, каждая OTA и выбранный член rootfs проверяются
по SHA-256. `prepare.py` читает CPIO (на Mini 1 внутри tar.xz); UBIFS
извлекается с сохранением inode-прав, а принятый образ Миди `rootfs.ext4.gz`
передаётся непосредственно в `kuyase prepare` без монтирования на хосте.
На Mini 1 штатный `adbd_backup` копируется как `adbd`.
Исходные установщики OTA не запускаются. VM работает в stub/snapshot на
временном GitHub-hosted runner без секретов; checkout не сохраняет Git-учётные
данные. В локальной CI-сборке КУЯСЭ задан QEMU user-net `restrict=on`; нет TAP,
сохраняются только пробросы с loopback хоста, нужные контроллеру и ADB.

Распознавание и облачные ответы здесь синтетические. Проверяется запрос TTS,
но аудиопоток не синтезируется. Передача аудио, физический DAC, iPhone,
обнаружение mDNS в локальной сети, реальные облачные сервисы и Home Assistant
требуют отдельных испытаний. Установщик и обновление пакетов этим набором
также не проверяются. В сценариях `local_progress` выключен. Повторное
открытие микрофона после ответа LLM не проверяется.

## Локальный запуск

Нужны Linux, `qemu-system-aarch64`, `adb`, `curl`, Python 3, Go, Node.js с npm и OpenSSL, а также
Rust/rustup и native build dependencies из workflow.

```sh
(cd scripts/web-screenshots && npm ci --ignore-scripts --no-audit --no-fund && npx --no-install playwright install --with-deps chromium)
python3 -m venv runtime/kuyase-ci-venv
runtime/kuyase-ci-venv/bin/pip install ubi-reader==0.8.16
rustup toolchain install stable --profile minimal
bash scripts/kuyase/build-emulator.sh runtime/kuyase-ci
runtime/kuyase-ci-venv/bin/python scripts/kuyase/prepare.py \
  --board station2 --emulator-dir runtime/kuyase-ci --output runtime/kuyase-ci-input
python3 scripts/build-speaker-package.py --arch arm64
python3 scripts/build-speaker-package.py --arch armv7
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o dist/kuyase-control ./scripts/kuyase/control
python3 scripts/kuyase/run.py --board station2 --arch arm64 \
  --emulator-dir runtime/kuyase-ci --build-dir dist --output dist/kuyase-results/station2-arm64
```

Без `--arch` обе сборки проверяются последовательно с новым экземпляром
фикстур для каждой сборки. Порты хоста `127.0.0.1:15555`, `18090`, `18091`
должны быть свободны. Скрипт завершает только созданные им процессы VM;
существующие VM и физические колонки не останавливает.

Контроллер и отчётность можно проверить без VM:

```sh
go test -race ./scripts/kuyase/control -count=1 -timeout=60s
python3 -m unittest discover -s scripts/kuyase -p 'test_*.py'
```

Go-тест контроллера использует Proxy/Native/Engine и HTTP-клиенты LLM/MCP,
но не standalone-процесс и не настоящий приёмник. E2E-совместимость прошивки
подтверждает только отдельный прогон VM.
