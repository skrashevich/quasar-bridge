# Проверки и ограничения

## Веб-панель управления

Локальная проверка панели от 2026-11-13:

- `go test ./...`, `go test -race ./... -count=1 -timeout=90s`, `go vet ./...`;
- обычная сборка и `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build`;
- `node --check cmd/quasar-bridge/diagnostics.js` и `-check-config` для общего
  и колоночного конфигов-примеров;
- HTTP-запросы к настоящему бинарнику: сетевой порт закрыт по умолчанию,
  открывается после сохранения и reload, закрывается после обратного изменения;
  уже открытое сетевое соединение после отключения получает HTTP 403;
- браузер с локальным тестовым LLM: сохранение/reload, сохранность черновиков,
  отклонение неверных значений, статическая проверка маршрута и выполнение
  запроса, поиск истории за один день, недоступный AirPlay, пауза/поиск/скачивание
  журнала, широкая вёрстка и все разделы на ширине 360 px без переполнения.

Автотесты дополнительно проверяют голосовой вызов настройки и reload,
проверку Origin и сетевых адресов, откат при ошибке порта, сериализацию запросов
между двумя HTTP-серверами, изоляцию тестового диалога и ограничения JSON.
Регрессия с настоящими сокетами подтверждает, что панель не занимает порт
основного сервера, если существующая установка уже использует порт 8080.

Дополнение с аналогами CLI проверено через настоящий бинарник и локальный
LLM-бэкенд: ответы API `decide` и `query` совпадают с `-route` и `-query`,
включая режим `observe` и успешную классификацию. В браузере проверены все три
кнопки тестирования, JSON решения, блокировка редактирования во время
классификации и отсутствие переполнения на ширине 360 px. API race-тесты
дополнительно проверяют распознавание команды AirPlay без её выполнения,
резервный маршрут при ошибке классификатора и общую блокировку `decide`/`query`.

Новая панель и голосовое переключение сетевого доступа на физической колонке
в этом прогоне не проверялись; сборка на колонку не устанавливалась.

## Предыдущие проверки на колонке

В живом пилоте на rooted Station 2 подтверждены:

- доверие локальному CA, подключение к Go-прокси и переподключение;
- штатный текстовый запрос с ответом Яндекса и передачей аудио;
- запрос через микрофон, ответ собственной LLM и слышимое озвучивание;
- замена текстового отказа Алисы ответом LLM и подавление старого TTS;
- голосовое чтение Home Assistant, сверенное с текущими состояниями;
- физическое выключение основного света и отдельного светильника через
  работающий Go-сервер, с независимой проверкой `on` → `off` в HA.

Общая команда сначала выключила основную группу, но пропустила отдельный
светильник. Явная команда для него завершила выключение. Это известное
ограничение выбора целей LLM; проверка каждой выбранной цели не гарантирует
полноту покрытия комнаты.

Во время пилота ответы HA занимали порядка 10–17 секунд. Короткий тайм-аут
внешнего `sendText` мог истечь раньше завершения и озвучивания; такой тайм-аут
сам по себе не доказывает ни успех, ни отказ исполнения.

Автоматические проверки: `go test -race ./...`, `go vet ./...`.
Fixtures покрывают:

- передачу WebSocket payload/query/auth и неизвестных сообщений;
- четырёхбайтовый AAPI marker, неизвестные/дублирующиеся protobuf-поля;
- text/voice, финальный и пустой ASR, единственный обработчик, TTS/audio;
- отмену, поздний Continue и повторное использование stream ID;
- замену отказа с TTS-заглушкой и сохранение исполнительных директив;
- ошибки/cancellation LLM, отсутствие URL в транспортных ошибках;
- MCP SSE, ошибки внутри HTTP 200 и конкурентные чтения;
- целевые сущности, разрешения Assist, группы, пересечения и неподтверждённые действия;
- изоляцию вопросов о состоянии и подготовки кеша от физических действий;
- конфигурацию/переопределения окружением и отклонение неверных настроек.

Режим без Home Assistant дополнительно проверяется отдельным процессом:
запуск `hybrid`, `/healthz`, `-check-config`, `-check-backends`, `-route` и
генерация `-query` через HTTP fixture OpenAI API. Пустой MCP URL отключает HA,
невалидный непустой отклоняется. Правила, default и оба исхода классификатора
передают `home` в Яндекс; Native text/voice сохраняет облачный путь и Continue.
Настроенный HA при ошибке не вызывает повторного облачного исполнения.
Это автоматические проверки; действующая колонка с HA для этого режима
не перенастраивалась.

## Пользовательские MCP-серверы

SDK fixtures проверяют Streamable HTTP и SSE с авторизацией, stdio-процесс,
discovery и фильтры, одинаковые имена инструментов у разных серверов, точность
больших целых аргументов и повтор одинакового изменяющего вызова. Ошибки,
тайм-ауты, недоступный сервер, запрет redirects и перехода SSE на другой origin,
а также блокировка MCP после приватной истории проверяются отдельно.
Процессная проверка CLI покрывает `-check-mcp` без исполнения инструментов и
полный путь `-query` → HTTP API LLM → MCP → окончательный ответ.

На внешнем `https://search.parallel.ai/mcp` подтверждены discovery двух
инструментов (`web_search`, `web_fetch`) и настоящий вызов `web_search` нашей
LLM через Go-сервер. Запрос искал официальную документацию `context.WithTimeout`;
поиск отвечал примерно за 1,1 секунды. При `max_result_chars: 3000` LLM вернула
окончательный ответ с официальным источником. Прогон с лимитом 12000 символов
превысил общий 65-секундный бюджет на второй генерации; ограничение результата
не отменяет зависимость от скорости выбранной модели. На физической колонке
эта функция пока не проверялась.

Музыка, таймеры, многочасовая стабильность, все модели колонок и все варианты
отказов не проверены полностью. Неизвестные формы протокола проходят в Яндекс.
Это выборочный гибридный сервер, а не полная замена всех облачных API.

Персональные адреса, серийные номера, сущности HA, токены, сертификаты и журналы
конкретного стенда намеренно не входят в репозиторий.

Настраиваемая маршрутизация дополнительно проверена:

- сочетания условий, порядок/отключение правил и RE2 regex;
- наследование defaults, полная замена массива правил и пример конфигурации;
- настройки классификатора/отказов, конкурентная замена политик без гонок;
- сохранение снимка во время уже начавшейся классификации;
- смена маршрута и обработки отказов в существующей Native-сессии;
- отдельный процесс с настоящим SIGHUP и сохранением последней исправной политики;
- диагностические CLI-флаги без исполнения домашних действий;
- живой Linux-пилот: reload изменил revision без смены PID, ошибочный regex
  был отклонён без замены политики, исходные правила затем восстановлены.

## Потоковое ожидание локальных ответов

На rooted Station 2 проверен серверный режим `local_progress` с ответом LLM,
искусственно задержанным на 20 секунд. Команда отправлена через `sendText`:
после начальной фразы ожидания SDK сохранял поток активным и подтвердил
завершённое проигрывание после получения окончательного ответа, без ошибки
15-секундного VINS timeout. Подтверждение слухом для этого нового режима
фиксируется отдельно от автоматической проверки. Прошивочный конфиг не менялся.

Регрессионные проверки дополнительно покрывают объединение двух Ogg/Opus
сегментов и тишины, CRC, порядок страниц и granule positions, end padding,
повторное использование stream ID между сегментами, финальный Close,
отмену, быстрый локальный ответ и сохранение обычного маршрута Яндекса.

## Беззвучное ожидание (0.3.4)

Промежуточные сообщения не содержат текста для озвучивания. Начальный
синтез используется только для получения совместимых Opus-заголовков;
все его речевые пакеты отбрасываются. Далее сервер передаёт синтетическую
тишину до готовности настоящего ответа. Его аудио добавляется в тот же поток.

Регрессии покрывают отсутствие промежуточного текста и утечки начальных
речевых пакетов, сохранение финальной озвучки, повторное использование
stream ID, text/voice-путь и отмену. Живой прогон на Station 2 подтвердил
полное воспроизведение ответа с этим началом потока без ошибки SDK.

Второй живой прогон 0.3.4: готовый ответ получен через 15,6 секунды;
SDK подтвердил завершённое проигрывание без таймаута. Все промежуточные
записи доставлены с пустым текстом. Слуховое подтверждение пользователя
для этого прогона отдельно не запрашивалось.
