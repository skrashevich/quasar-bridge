# Экспериментальный запуск на Android

Отдельный пакет позволяет запускать Bridge на Android-колонке с root-доступом.
Проверка выполнена на Станции Макс: Android 9 / API 28, ядро 4.9, ARM64,
SELinux permissive. Совместимость с другими прошивками и SELinux enforcing
требует отдельной проверки.

На устройстве подтверждены установка, запуск службы, healthcheck и настоящий
текстовый ответ Яндекса, в том числе через локальный WebSocket-прокси Bridge.
В живом микрофонном прогоне распознано «Сколько будет 7 + 8?»; ответ `15`
прошёл через Bridge, а native перешёл в `SPEAKING`. Физическая слышимость
пока не подтверждена отдельно пользователем. До установки
штатная Алиса не работала: `maind --yiod` аварийно завершался при чтении
неполной сохранённой конфигурации. Запуск восстановлен отдельно от Bridge
(см. ниже); текстовый запрос сам по себе не проверяет голосовой тракт.

## Требования

- Root по SSH, ARM64 и возможность выполнить статический Linux ELF.
- Рабочая штатная Алиса для последующей проверки голоса.
- `sh`, `tar`, `readlink -f`, `stat -c`, `mount -o bind`, `umount`, `getprop`.
- Конфигурация `/system/vendor/quasar/quasar.cfg` с разделом `aliced`.
- Доступный DNS-сервер и комплект доверенных сертификатов прошивки.

Пакет использует статическую сборку `GOOS=linux`, поэтому NDK и установка APK
для Bridge не требуются. Настройки DNS задаются только для процесса Bridge:
обычный Go resolver иначе обращается к отсутствующему локальному DNS.
Android launcher также включает `QUASAR_ANDROID_BACKEND_PROXY=1`: локальный
relay настроек нужен старой прошивке, в которой облачный `uniProxyUrl`
перекрывает endpoint из файла прошивки.

`QUASAR_DNS_SERVER` принимает числовой IP с необязательным портом, включая
`[IPv6]:port`; по умолчанию launcher читает `getprop net.dns1`, затем `net.dns2`.
На прошивках, где эти свойства пусты, укажите сервер явно в `runtime.env`.

## Сборка и передача

На компьютере в checkout нужной ветки:

```sh
python3 scripts/build-android-package.py
```

Результат: `dist/quasar-bridge-android-arm64.tar.gz` и файл SHA-256 рядом.
Сборка имеет версию `dev`. Установщик проверяет эту версию; автоматическая
установка стандартных Linux-архивов на Android блокируется также маркером
`app/PLATFORM`.

Передача через SSH работает и с Dropbear без серверного `scp`:

```sh
ssh -p 2222 root@SPEAKER_IP \
  'mkdir -p /data/local/tmp/quasar-bridge-package; chmod 700 /data/local/tmp/quasar-bridge-package; cat > /data/local/tmp/quasar-bridge-package/package.tar.gz' \
  < dist/quasar-bridge-android-arm64.tar.gz
ssh -p 2222 root@SPEAKER_IP \
  'cd /data/local/tmp/quasar-bridge-package && tar -xzf package.tar.gz && sh install.sh'
```

Установщик размещает приложение в `/data/opt/quasar-bridge-android/app`,
настройки — в `/data/opt/quasar-bridge-android/config.json`.
Существующую установку он сохраняет и отказывается заменять автоматически.

## Проверка и запуск

Дальнейшие команды выполняются на колонке под root:

```sh
sh /data/opt/quasar-bridge-android/app/control.sh check
sh /data/opt/quasar-bridge-android/app/control.sh start
sh /data/opt/quasar-bridge-android/app/control.sh status
sh /data/opt/quasar-bridge-android/app/start.sh -query 'Сколько будет два плюс два?'
```

Пакет начинает в `observe`: запросы идут в Яндекс. Интерфейсы слушают loopback;
для веб-панели можно использовать SSH-туннель:

```sh
ssh -p 2222 -L 2704:127.0.0.1:2704 root@SPEAKER_IP
```

Откройте `http://127.0.0.1:2704` на компьютере. Для нейросети настройте `hybrid`
и параметры LLM по основному руководству, сохранив `airplay.disabled: true`.
Секреты можно разместить в `runtime.env` рядом с конфигурацией (режим `0600`).
Например, туда же добавляются `QUASAR_DNS_SERVER` или `SSL_CERT_FILE` при
необходимости изменить значения launcher. После изменения выполните `restart`.

## Подключение штатной Алисы

Сначала убедитесь, что `status` успешен и обычная Алиса работает.
Примените временную подмену:

```sh
sh /data/opt/quasar-bridge-android/app/control.sh apply
```

Controller проверяет наличие работающего relay, копирует разрешённую цель
симлинка `quasar.cfg` и меняет в копии `aliced.uniProxyUrl` и
`common.backendUrl`. Копия накладывается через bind mount на исходный путь.
Содержимое vendor и сам симлинк сохраняются. Перед применением он отказывается перекрывать
существующий mount, а при откате сверяет mount и inode своей копии.
Чтение таблицы mount выполняется средствами shell: штатный `awk` на проверенной
прошивке аварийно завершался.

Relay доступен только на loopback основного listener по `/android-backend/`.
Он пересылает запросы на фиксированный `https://quasar.yandex.net` с проверкой
TLS. В успешном ответе `/get_sync_info` меняется только
`config.system_config.uniProxyUrl`; остальные настройки остаются облачными.
Остальные backend-запросы проходят с исходными данными. Перенаправления
отклоняются, чтобы OAuth-заголовок не ушёл на другой origin. Listener панели
этого маршрута не предоставляет.

После этого требуется ручной перезапуск **конкретного голосового процесса**
прошивки. На проверенном устройстве это `maind --yiod`, запускаемый
`quasar_launcher`; Android-приложение отдельно обслуживает интерфейс.
Способ перезапуска зависит от прошивки, поэтому controller его не выполняет.
Обратитесь к журналам launcher и проверьте, что голосовой процесс остаётся жив.

Перед откатом остановите штатный `yiod` способом своей прошивки и удерживайте
его остановленным, включая автоматические перезапуски supervisor, до завершения
операции. Живой процесс хранит локальный backend в памяти и может записать его
обратно в кеш. Controller не управляет штатным supervisor автоматически.

Сам Bridge оставьте работающим до окончания отката:

```sh
# Сначала остановите yiod и его автоматические перезапуски.
sh /data/opt/quasar-bridge-android/app/control.sh rollback
# После успешного отката верните штатный запуск yiod.
# Убедитесь, что он подключился к Яндексу с исходными настройками.
sh /data/opt/quasar-bridge-android/app/control.sh stop
```

Помимо снятия mount, rollback восстанавливает `system_config.uniProxyUrl` в
нативном protobuf-кеше, если значение совпадает с URL этого bridge. Остальные
поля, аккаунты и неизвестные protobuf-поля сохраняются. Перед заменой создаётся
приватная побайтная копия в `backups/`; смена файла выполняется атомарно.
Если native writer работает или исправление кеша не удалось, операция сообщает
об ошибке и сохраняет файлы учёта для повторной попытки. Проверка процессов
дополняет обязанность удерживать supervisor остановленным: это не блокировка,
согласованная с самим `syncd`.

Стандартный путь кеша — `/data/quasar/data/user_config.dat`; для иной прошивки
можно указать `QUASAR_NATIVE_CONFIG_STORAGE`. На Максе проверен полный
цикл: остановка native writer при приостановленном supervisor, снятие mount,
восстановление официального endpoint в реальном кеше, остановка Bridge и
повторный запуск `yiod` штатным launcher. Native открыл прямое соединение
с Яндексом; контрольная сумма vendor-файла и исходный симлинк сохранились.
Также проверен отказ helper без изменения кеша при работающем `yiod`.


После перезагрузки исчезает только bind mount; локальный endpoint в
нативном protobuf-кеше может сохраниться. Автозапуск пакетом не устанавливается.
В таком случае также выполните `rollback`, предварительно остановив native
writer и его supervisor, чтобы восстановить кеш и убрать файлы учёта.
При прерванной операции проверьте процессы, mount и `service.lock` в каталоге
состояния перед ручным удалением устаревшей блокировки.

## Ограничения и проверки

AirPlay отключён: текущие PCM-модули используют glibc/ALSA, а Android — Bionic.
Автообновление и автоматический откат endpoint с перезагрузкой недоступны;
обновление пакета и откат выполняются вручную. Обычный `restart` Bridge и
переключение в `observe` остаются доступны.

`-query` сам обращается к Яндексу и не доказывает прохождение голосовых кадров
через прокси. Отдельный проверочный клиент на устройстве отправил настоящий
текстовый протокол через `ws://127.0.0.1:8443/uni.ws` в режиме `observe` и получил
ответ `4`. Это подтверждает сетевой прокси, но не микрофон, TTS, Home Assistant
или настоящую LLM.

Локальные проверки изменений:

```sh
go test -race ./... -count=1 -timeout=60s
go vet ./...
python3 scripts/test-android-package.py
```

Устройство также проверено циклом `apply` → `rollback` с сохранением исходной
SHA-256 vendor-конфигурации и симлинка. Исходная конфигурация пользователя
сохранена отдельно; последующее восстановление штатного `yiod` описано ниже.

## Восстановление штатного yiod на проверенной прошивке

На исследованной Станции Макс (Android 9, прошивка `3.21`, сборка Android
`PPR1.180610.011.20201111`) процесс падал с исключением:

```text
Cannot get json field 'account_config' from json. Field is not present
```

`/data/quasar/data/user_config.dat` — protobuf `ConfigStorage`, а JSON находится
в `UserConfig.config` активного аккаунта. В исходном файле этот JSON содержал
только настройки ADB и не содержал `account_config`. Полная замена файла
обычным JSON повредит формат хранения.

Разбор соответствующей сборки `maind` показал два обязательных строковых
поля: `account_config.contentAccess` и `account_config.spotter`. Их собственные
значения по умолчанию в конструкторе этой прошивки — `medium` и `alisa`.
Временная копия исходного protobuf с этими двумя полями позволила запустить
`yiod`. После запуска его штатный `syncd` скачал актуальную полную конфигурацию
из облака. На постоянное место сохранён именно этот облачный protobuf;
временный bind mount снят. Данные других аккаунтов и protobuf-поля при
подготовке временной копии сохранялись.

Исходный файл и полученная облачная конфигурация оставлены в приватном каталоге
`/data/opt/quasar-bridge-android/backups/yiod/` с режимами `0700`/`0600`.
Эти файлы содержат пользовательские настройки и не входят в исходники
или архив приложения. Прошивка продолжает обновлять настройки штатно.
После восстановления подтверждены запуск `yiod` штатным `quasar_launcher`,
активный детектор «Алиса» и двусторонние кадры native-соединения через Bridge
в режиме `observe`. В живом запросе ASR распознал «Сколько будет 7 + 8?», затем журнал зафиксировал
`output_speech: "15"` и состояние `SPEAKING`; счётчики Bridge подтвердили
трафик в обе стороны. Отдельного подтверждения слышимости от пользователя
пока нет. Проверка выполнена в `observe`, без внешней LLM и Home Assistant.
После теста полный откат endpoint и кеша выполнен, Bridge остановлен,
штатный `yiod` работает с прямым Яндексом. Исправленная полная облачная
конфигурация остаётся на колонке; исходный повреждённый файл сохранён в backup.

Это ремонт конкретного повреждённого состояния, а не универсальный установочный
шаг: Android-пакет не изменяет `user_config.dat` автоматически. При аналогичном
симптоме сначала проверьте исключение, текущую схему и значения конкретной
прошивки; сохраните побайтную резервную копию до исправления.
