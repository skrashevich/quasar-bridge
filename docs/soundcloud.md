# SoundCloud

SoundCloud — включаемый отдельно музыкальный провайдер для гибридного режима.
Поиск, доступ к каталогу, переписывание HLS, проксирование обложек и управление
очередью выполняются внутри Go-приложения. Python, yt-dlp, ffmpeg, внешний декодер
и вспомогательный процесс не требуются. Байты аудио и кодеки сохраняются;
воспроизведение использует нативный `audio_play` колонки.

## Настройка через установщик

В интерактивной установке после подключения нейросети и Home Assistant можно
выбрать режим SoundCloud:

| Режим | `enabled` | `default` | `compare_yandex` |
| --- | --- | --- | --- |
| Отключён | `false` | `false` | `false` |
| Только по явному запросу SoundCloud | `true` | `false` | `false` |
| SoundCloud по умолчанию | `true` | `true` | `false` |
| Сравнение с предпочтением Яндекса при равенстве | `true` | `false` | `true` |
| Сравнение с предпочтением SoundCloud при равенстве | `true` | `true` | `true` |

Enter сохраняет существующую настройку; в новой конфигурации SoundCloud остаётся
отключённым. Для нового включённого провайдера установщик выбирает публичный
`api: web`, не требующий учётных данных. При перенастройке сохраняются ранее
заданные API, токены, `base_url`, лимит очереди и остальные параметры. Обновление
без изменения настроек также сохраняет конфигурацию. Чтобы включить SoundCloud
позже, повторите установку с изменением настроек либо добавьте блок вручную.

В меню SoundCloud пункт `6` подключает личный аккаунт, пункт `7` отключает его.
Установщик принимает токен скрытым вводом и проверяет аккаунт до сохранения.
Режимы выбора провайдера и сравнения сохраняются; для нового подключения
SoundCloud включается с явными запросами. После установки служба перезапускается.

## Настройка вручную

Добавьте этот объект в рабочую конфигурацию гибридного режима:

```json
{
  "soundcloud": {
    "enabled": true,
    "default": false,
    "api": "auto",
    "queue_limit": 50,
    "base_url": "http://speaker.example.invalid:8443"
  }
}
```

Замените адрес из примера на адрес, с которого фактически доступен Bridge.
`base_url` должен быть источником HTTP(S) без пути, учётных данных, строки запроса
и фрагмента. Отдельный слушатель не открывается: `/soundcloud/` использует
существующие настройки `listen` и TLS Bridge. Колонка должна иметь доступ к этому
адресу; если обложки нужны клиентам телефона или Home Assistant, доступ необходим
и им. Настройте `listen`, маршрутизацию и `allowed_ips` соответствующим образом.
Для слушателя TLS нужен доступный HTTPS-адрес и сертификат, которому доверяют
клиенты, либо явно настроенный адрес обратного прокси.

Если `base_url` не указан, для слушателя на loopback выводится обычный HTTP. Это
подходит для воспроизведения, когда Bridge работает на колонке. Телефон не сможет
получить обложку с колонки через `127.0.0.1` или `localhost`; для внешних
потребителей обложек укажите доступный адрес. Включённый провайдер отклоняет внешний
слушатель или слушатель TLS без `base_url`, а также режим наблюдения. При
отключённом SoundCloud существующее поведение слушателя не меняется. Параметры
`assistant_tools.enabled` и `assistant_tools.play_sound` этим провайдером не
управляют.

## SOCKS5-прокси

При установке или обновлении с включённым SoundCloud мастер проверяет доступ
к нему с самой колонки. Если проверка не прошла, мастер предлагает ввести
SOCKS5-адрес. Ввод скрыт, поскольку URL может содержать логин и пароль.
Проверяется не только соединение с прокси, но и настоящий поиск SoundCloud,
HLS-плейлист и первый фрагмент аудио; обложка проверяется при её наличии.
Проверка ограничена 15 секундами и не запускает музыку на колонке.

Неработающий адрес можно исправить и повторить проверку. Только успешно
проверенный прокси сохраняется в закрытом `runtime.env`; Enter оставляет
прежние настройки и позволяет продолжить установку. При отмене установки
прежние настройки восстанавливаются. Ошибка проверки также может быть связана
с авторизацией SoundCloud, поэтому она сама по себе не означает блокировку.

Для SoundCloud можно отдельно задать SOCKS5-прокси, доступный с устройства,
на котором работает Bridge. Добавьте `proxy_url` в существующий блок:

```json
{
  "soundcloud": {
    "enabled": true,
    "api": "web",
    "proxy_url": "socks5h://proxy.example.invalid:1080"
  }
}
```

Замените адрес и порт своими. Поддерживаются `socks5://` и `socks5h://`;
в обоих случаях имена серверов SoundCloud передаются прокси для разрешения DNS.
Для авторизации используйте
`socks5h://login:password@proxy.example.invalid:1080`. Специальные символы в
логине и пароле должны быть закодированы для URL, например `@` как `%40`.

Вместо JSON можно добавить в `/data/opt/quasar-bridge/runtime.env`:

```sh
QUASAR_SOUNDCLOUD_PROXY_URL='socks5h://login:password@proxy.example.invalid:1080'
```

Переменная окружения имеет приоритет над JSON. Пустое значение возвращает
обычные сетевые настройки. После изменения перезапустите Bridge:

```sh
sh /data/opt/quasar-bridge/app/control.sh restart
```

Через этот прокси идут все внешние запросы SoundCloud: публичный каталог,
обнаружение client ID, OAuth и обновление токенов, сведения о треках, HLS-плейлисты,
сегменты аудио и обложки. Соединения колонки с локальным Bridge, Яндексом,
нейросетью и Home Assistant сохраняют прежний маршрут. TLS-проверка сертификатов
сохраняется. Если заданный прокси недоступен, запрос завершается ошибкой;
прямого подключения к SoundCloud в обход него нет.

Адрес и реквизиты прокси не включаются в `/healthz` и сообщения ошибок.
Храните конфигурацию с закрытыми правами и не публикуйте реальные реквизиты.
Повторная установка с сохранением настроек сохраняет `proxy_url` и переменную
окружения.

## Маршрутизация и команды

При `default: false` запрашивайте SoundCloud явно, например: «включи SoundCloud
Daft Punk». При `default: true` запросы музыки без указания провайдера, например
«включи песню …», также используют SoundCloud. Явные запросы Яндекса, AirPlay и
других сайтов остаются доступными. Команды управления активным AirPlay сохраняют
приоритет. После перехвата запроса SoundCloud недоступный трек или ошибка каталога
вызывает локальную ошибку SoundCloud, а не запуск трека Яндекса.

Провайдера по умолчанию также можно изменить голосом без перезапуска Bridge:

- «Алиса, включи SoundCloud по умолчанию».
- «Алиса, используй Саундклауд по умолчанию».
- «Алиса, верни Яндекс Музыку по умолчанию».
- «Алиса, какой музыкальный сервис по умолчанию?»

Эти команды обрабатываются локально до языковой модели, в том числе при
отключённых инструментах ассистента. При успешном изменении атомарно сохраняется
только `soundcloud.default`, предыдущая конфигурация остаётся в закрытой резервной
копии `.voice-backup`, а новые запросы музыки без указания провайдера сразу
используют новый вариант. Текущее воспроизведение и очереди сохраняются. Настройка
переживает перезапуск Bridge и применяется к этому экземпляру Bridge. Для выбора
SoundCloud провайдер должен быть включён и активен. Ошибка сохранения не меняет
текущее значение по умолчанию. Явное указание провайдера по-прежнему имеет
приоритет; `/healthz` сообщает текущее логическое значение в
`soundcloud.default`.

## Сравнение выбора Алисы с SoundCloud

Установите `soundcloud.compare_yandex` в `true`, чтобы параллельно сравнивать
результаты запросов конкретной песни, например «включи песню Гусары, орать».
По умолчанию параметр отключён. Сравнение получает **один трек Яндекса, выбранный
Алисой**, и кандидатов SoundCloud; полный список результатов поиска Яндекса не
запрашивается и не объединяется.

### Какие запросы сравниваются

Сравнение работает для запроса конкретной песни без указания сервиса, например
«Алиса, включи песню Гусары орать». SoundCloud ищется параллельно с однократным
исходным запросом Алисе. Явные запросы провайдера, ссылки, плейлисты, исполнители,
запросы только для поиска, команды управления и настройки сохраняют свою
маршрутизацию. Общие запросы вроде «включи музыку» и «включи что-нибудь весёлое»
сохраняют обычный музыкальный сценарий. Команды управления активным AirPlay имеют
приоритет.

### Подготовка кандидатов

Короткая команда без слова «песню», например «включи нас нет», допускается к
сравнению после того, как обычный классификатор направил её Яндексу. Для неё
SoundCloud должен найти точное нормализованное название, возможно вместе с
исполнителем; частичного совпадения недостаточно. Правила маршрутизации,
управление домом и служебные команды сохраняют приоритет.

Яндекс предоставляет один выбранный Алисой трек. В SoundCloud запрашивается до
`queue_limit` результатов (по умолчанию 50, допустимо 1–100), которые сортируются
по убыванию общей оценки, описанной ниже. При равных оценках сохраняется исходный
порядок каталога SoundCloud. Выбирается первый кандидат с положительной
длительностью, для которого удалось получить доступный полный поток. Недоступные
записи пропускаются; другая ошибка разрешения потока завершает подготовку с
ошибкой. До победы подготовка не изменяет активную очередь.

Для короткой команды, если колонка сообщает о текущем потоке своей очереди
SoundCloud, выполняется также поиск по названию и исполнителю этого потока.
В дополнительном поиске достаточно первых десяти результатов (или меньшего
`queue_limit`). Точные совпадения этого исполнителя из текущей очереди также
участвуют в выборе; доступность их аудиопотока проверяется заново.
Это работает и после естественного окончания трека, пока сеанс не истёк и не
передан другому источнику. Результаты объединяются без дубликатов и ограничиваются
`queue_limit`; при равной оценке предпочитается этот исполнитель. Более высокая
оценка другого трека сохраняет приоритет. Без такого контекста исполнитель не
угадывается, поэтому одноимённые песни по-прежнему могут требовать уточнения
исполнителя. Правило равенства между провайдерами остаётся прежним.

Если дополнительный поиск завершился ошибкой или тайм-аутом, чужая одноимённая
песня из общего поиска не заменяет ожидаемый результат: остаются точные кандидаты
текущего исполнителя либо трек с явно названным исполнителем. Если таких нет,
сохраняется ответ Яндекса. Успешный пустой поиск по исполнителю отличается от
ошибки и допускает обычный выбор из общего поиска.

### Нормализация запроса и метаданных

Правила одинаковы для обоих провайдеров и реализованы в
[`internal/musicmatch`](../internal/musicmatch/match.go):

- Буквы переводятся в нижний регистр, `ё` заменяется на `е`. Пунктуация и прочие
  символы, кроме букв и цифр, заменяются пробелами; повторные пробелы объединяются.
- Из начала запроса удаляются «Алиса», один глагол запуска («включи», «поставь»,
  «сыграй», «играй», «запусти», `play`) и следующее за ним обозначение «песню»,
  «трек», «композицию», `song` или `track`, если они присутствуют.
- Обозначения версий приводятся к общей форме: «ремикс» → `remix`, «кавер» →
  `cover`, «концертная версия»/«концерт» → `live`, «караоке» → `karaoke`,
  «инструментальная версия» → `instrumental`.
- Из названия убирается совпадающий префикс исполнителя, в том числе после
  числового номера длиной до трёх цифр. Например, при исполнителе `svk` название
  «03 svk - Не спать!» сравнивается как «не спать».

### Как начисляются баллы

Оценка начинается с нуля. Сначала учитывается каждое слово нормализованного
запроса, затем один бонус за форму совпадения, затем поправки за версии.

| Критерий | Изменение оценки |
| --- | ---: |
| Слово запроса целиком присутствует в названии или имени исполнителя | +10 за каждое слово запроса |
| Слово запроса отсутствует и в названии, и в имени исполнителя | −20 за каждое слово запроса |
| Запрос точно равен «название исполнитель» или «исполнитель название» | +100 |
| Иначе: запрос точно равен названию | +90 |
| Иначе: запрос содержит название и непустое имя исполнителя | +70 |
| Иначе: название содержит запрос | +20 |
| Маркер версии есть в названии/поле версии и запрошен пользователем | +35 за каждый найденный маркер |
| Маркер версии есть в названии/поле версии, но не запрошен | −45 за каждый найденный маркер |
| Пустой запрос или пустое название после нормализации | Итог −10000 |

Бонусы +100/+90/+70/+20 взаимоисключающие: применяется первый подходящий в порядке
таблицы. Проверка слов использует целые слова, а проверки «содержит» для бонусов
+70 и +20 — буквальную подстроку. Маркеры версий: `cover`, `remix`, `live`,
`karaoke`, `instrumental`, `sped up`, `slowed`, `nightcore` и их указанные выше
русские эквиваленты. Наличие нескольких разных маркеров суммирует поправки.

Например, для «Гусары орать» запись «Гусары, Орать!» исполнителя `svk` получает
`2 × 10 + 90 = 110`. Название «Гусары» с исполнителем, в имени которого нет
«орать», получает `10 − 20 = −10`. Для запроса `Song` оригинал с названием `Song`
получит 100 баллов, а `Song (remix)` без запрошенного ремикса — `10 + 20 − 45 = −15`.

### Выбор победителя и ограничения

Подготовленный кандидат SoundCloud сравнивается с выбранным треком Яндекса по
одной и той же формуле. Побеждает большая оценка. При точном равенстве используется
текущий провайдер по умолчанию: `soundcloud.default: true` выбирает SoundCloud,
`false` — Яндекс. При включённом сравнении провайдер по умолчанию разрешает
равенство, а не перевешивает более точное совпадение.

Это лексическое сравнение метаданных: оно не использует LLM, прослушивание аудио,
популярность, число прослушиваний, битрейт или предположение о качестве сервиса.
Длительность служит условием подготовки SoundCloud, но не добавляет баллы.
Исправление опечаток, транслитерация, морфология и минимальный порог уверенности
не реализованы: если оба результата имеют низкую оценку, всё равно выбирается
большая из них. Поэтому «самый релевантный» здесь означает лучший из доступных
кандидатов по этой формуле, а не гарантированное совпадение записи.

Нативное сравнение ждёт не более трёх секунд и выпускает только один сценарий
воспроизведения. Неподдерживаемый формат ответа Яндекса, ошибка или тайм-аут
SoundCloud сохраняют обычный путь Яндекса. Если к моменту истечения срока
SoundCloud готов, а результат Яндекса отсутствует, он может победить после отмены
облачного запроса. Кандидат SoundCloud полностью разрешается до возможной победы;
подготовка проигравшего кандидата не изменяет существующую очередь. При победе
Яндекса сохраняются все его нативные метаданные и обратные вызовы. Отдельный OAuth-
токен Яндекса для нового режима не нужен. `/healthz` сообщает об активном сравнении
в `soundcloud.compare_yandex`.

Если Яндекс завершил сценарий без трека, но SoundCloud подготовил поток, SoundCloud
также может победить. Новый пользовательский запрос отменяет ожидающее сравнение.
Связанные команды воспроизведения и озвучивания удерживаются до выбора, чтобы не
запустить обоих победителей. Закрытие известного входного микрофонного потока само
по себе не является музыкальным результатом и не прерывает сравнение.

В журнале `native_music_comparison` поля `yandex_score` и `soundcloud_score`
показывают рассчитанные оценки; `winner` — выбранный путь, `completed` — завершение
выбора/передачи без ошибки, а не подтверждение состояния плеера `PLAYING`.
`unsupported_layout` и `reason` объясняют защитный переход
к Яндексу. Значение −10000 в журнале также используется, если соответствующий
кандидат ещё не получен: это не обязательно оценка найденного трека.

Пока сравнение ожидается, неизвестные музыкальные форматы сохраняют обычный путь
Яндекса. После победы SoundCloud запоздалые медиаданные проигравшего запроса
помещаются в карантин не более чем на 90 секунд. В это время подавляются и
действительно неатрибутированные TTS/сырое аудио; распознанная несвязанная сервисная
речь Push и локальный TTS продолжают доставляться. Известное новое воспроизведение
Яндекса снимает карантин. Это консервативное правило требует проверки на каждой
прошивке и не означает поддержку произвольных форматов звуковых уведомлений без
ссылок на запрос.

В тесте на Станции 2 запрос «включи песню Гусары орать» выбрал точную запись
SoundCloud пользователя `svk` вместо иначе названного результата Алисы из Яндекса.
Нативное воспроизведение сообщило состояние `PLAYING`, совпадающие
обложку/метаданные и растущую позицию. При втором сравнении для «Кукушка Кино» был
выбран Яндекс: оценки метаданных совпали, а Яндекс был предпочтительным провайдером.
После победы SoundCloud также работали явное воспроизведение из Яндекса и переход
к следующему треку. Это наблюдения при текстовой инъекции через локальный Alice IPC
на указанной ниже прошивке, а не акустическая проверка или проверка микрофонного
ASR. Реальный отложенный ответ содержал `@@mm_stack_engine_get_next` и точное
сервисное действие `uniproxy_action:update_memento`; при победе Яндекса они
сохраняются, а при победе SoundCloud удерживаются.

Провайдер поддерживает поиск и воспроизведение публичных треков, исполнителей,
альбомов/плейлистов, публичных ссылок SoundCloud, связанной музыки и ограниченную
очередь (по умолчанию 50, настраивается от 1 до 100). «Найди на SoundCloud …»
выводит результаты поиска без запуска воспроизведения; результат можно запустить
по номеру. В соответствующем сеансе SoundCloud доступны следующий/предыдущий трек,
пауза/продолжение/остановка, перемотка или перезапуск, повтор/случайный порядок и
сведения о текущем названии/исполнителе. Информация берётся из выбранного трека
каталога. Для личных отметок «Нравится» и их добавления/удаления требуется OAuth-
авторизация пользователя; при её отсутствии сообщается об отсутствии авторизации,
а успех не имитируется.

Название, исполнитель, длительность, обложка и метаданные Glagol относятся к одному
выбранному треку. Потоки и обратные вызовы получают новые идентификаторы сеанса
SoundCloud. Данные Яндекса `queue_item`, `playback_context` и учётные данные не
переиспользуются. Обратные вызовы жизненного цикла обрабатываются локально и
получают ответ без озвучивания. Вызовы finished/failed могут доставить следующий
трек даже после истечения срока исходного голосового запроса.

## Штатная музыкальная очередь UniProxy

Для SoundCloud Bridge обслуживает музыкальную серверную часть UniProxy:
выдаёт `audio_play`, принимает штатные события `music_thin_client_on_*`
(`started`, `stopped`, `finished`, `failed`), а продолжение очереди передаёт через
`@@mm_stack_engine_get_next`. Поиск, выбор трека, его метаданные и обложка
обслуживаются провайдером SoundCloud внутри того же Go-процесса.

Запрос с признаком `IsWarmUp` подготавливает один следующий трек. Ответ приходит
в связанном с запросом `AliceResponse`: колонка сохраняет его до завершения
текущего трека. Подготовка не переключает текущую песню; событие запуска или
состояние плеера подтверждает переход к следующей. Если продолжение ещё не было
доставлено, событие конца трека может запустить его отдельной директивой.
При большом оставшемся времени ранняя подготовка пропускается, чтобы ссылка
не успела истечь; при необходимости следующий трек разрешается после окончания
текущего.
Ошибки недоступных треков обрабатываются с ограниченным проходом по очереди.

Штатные команды плеера «продолжить», «следующий» и «предыдущий» поступают в
очередь структурированными командами. Название, исполнитель, длительность,
обложка и соседние треки обновляются вместе. События сопоставляются с колонкой,
сеансом и конкретным потоком: дубликаты и устаревшие события не переключают
новую музыку. Музыкальные сообщения активного Яндекса проходят в его сервер.

Очередь хранится в памяти Bridge. После его перезапуска запустите музыку заново;
служебное восстановление `music_thin_client_recovery` пока не восстанавливает
очередь автоматически. Набор поддержанных команд ограничен проверенным обменом
колонки, даже если protobuf-схемы содержат дополнительные возможности.

## Возможности новых protobuf-схем для SoundCloud

Bridge использует закреплённый снимок
[quasar-go-genproto](https://github.com/skrashevich/quasar-go-genproto/tree/5ec06bb3066cacea4b83daabbdd4fca83eaee80b).
Он сохраняет прежние wire-номера, Go API и JSON-имена и добавляет схемы новых
capability. В сборке используются готовые Go-типы: protoc и дополнительные
нативные компоненты не нужны.

Существующий SoundCloud продолжает работать через нативный
`client_action:audio_play`. Его `Payload` остаётся `Struct`/raw JSON; новая
endpoint-директива `audio_player_play_directive` относится к другому сценарию и
не может автоматически заменить этот формат.

Анализ новых типов выявил следующие направления развития SoundCloud. Они пока
не включены в обработку команд: сначала требуется проверить фактический обмен
конкретной прошивки.

| Новые типы | Что можно улучшить в SoundCloud | Что требуется проверить |
| --- | --- | --- |
| `TAudioPlayerCapability.TProgressEvent`, новое поле `PrefetchedTrack` | Согласование позиции и проигранного времени, сведения о предварительно загруженном треке | Привязку endpoint к колонке и своему stream ID; прежний `DeviceState.AudioPlayer` остаётся необходим |
| `PlayerControlCapability`: `TAvailableCommands`, `TPlayingState`, `TStreamInfo` | Согласование доступных кнопок next/previous/pause/resume/like и сведений о треке в приложении | Формат состояний и команд, которые принимает прошивка; поддержка SoundCloud с телефона пока не подтверждена |
| `MusicSearchCapability` с `TMusicSearchRequestDirective` | Работу с endpoint-поиском, содержащим несколько результатов | Транспорт и использование capability; RPC-типы списка результатов существовали и раньше, обычная Алиса по-прежнему возвращает один выбранный трек |
| `TMessageGroupInfo.SubRequestRefs` | Сопоставление отложенных музыкальных ответов с запросом сравнения | Однозначность владельца группы; неизвестный формат ответа сохраняет защитный путь Яндекса |

Наличие схем не доказывает поддержку этих сценариев колонкой и само по себе не
даёт полного списка поиска Яндекс Музыки для объединения с SoundCloud.

## Учётные данные каталога

Параметр `api` принимает значения `auto`, `official` и `web`. В режиме `auto`
при наличии реквизитов веб-сессии используется веб-API своего аккаунта. Иначе
официальный API используется при наличии официального токена доступа/обновления
либо client ID и секрета; в остальных случаях используется публичный веб-каталог. Публичный режим
обнаруживает и кэширует client ID публичного веб-клиента на Go и не требует учётных
данных аккаунта. Этот интерфейс может измениться и не заменяет авторизованный
доступ к закрытому содержимому.

Необязательные поля официального OAuth: `client_id`, `client_secret`,
`access_token`, `refresh_token` и `token_file`. Для веб-сессии предусмотрены
отдельные `web_access_token` и `web_token_file`. Значения окружения имеют приоритет
над соответствующими полями JSON:

- `QUASAR_SOUNDCLOUD_CLIENT_ID`
- `QUASAR_SOUNDCLOUD_CLIENT_SECRET`
- `QUASAR_SOUNDCLOUD_ACCESS_TOKEN`
- `QUASAR_SOUNDCLOUD_REFRESH_TOKEN`
- `QUASAR_SOUNDCLOUD_TOKEN_FILE`
- `QUASAR_SOUNDCLOUD_WEB_ACCESS_TOKEN`
- `QUASAR_SOUNDCLOUD_WEB_TOKEN_FILE`

Токен доступа или учётные данные клиента могут разрешить доступ к официальному
каталогу; для личных операций требуется авторизация пользователя. Токены обновления
позволяют выполнять ротацию. Необязательный `token_file` атомарно сохраняет
обновлённые токены с закрытыми правами файла. Храните учётные данные вне
зафиксированной в репозитории конфигурации. Состояние здоровья сообщает только
enabled/active/provider/API без значений токенов и секретов.

### Личный аккаунт без регистрации приложения

Для обычной учётной записи можно использовать `oauth_token` своей браузерной
сессии SoundCloud. Client ID/Secret собственного приложения и Artist Pro для
этого способа не нужны. Это подключение к веб-API сайта, которое может меняться.
Способ получения токена проверен по [Soundya](https://github.com/rodyatotu/soundya/blob/master/src/web.html);
Go-клиент Bridge реализован отдельно.

1. Откройте [SoundCloud](https://soundcloud.com/) на компьютере и войдите в свою
   учётную запись.
2. В инструментах разработчика браузера откройте **Application → Cookies →
   https://soundcloud.com**; в Safari — **Storage → Cookies**.
3. Скопируйте значение cookie **`oauth_token`**.
4. На уже установленной колонке откройте настройку аккаунта и выберите пункт `6`:

   ```sh
   sh /data/opt/quasar-bridge/app/setup.sh --soundcloud-account
   ```

   Вставьте токен в скрытое поле. Пароль аккаунта вводить не нужно. При ошибке
   проверки прежние реквизиты сохраняются. Отмена установки восстанавливает
   прежние настройки и файл сессии.

Этот режим меняет только подключение аккаунта и перезапускает Bridge. Повторная
настройка нейросети и переустановка пакета не нужны. При первоначальной установке
те же пункты `6` и `7` доступны в общем меню SoundCloud.

По умолчанию веб-сессия хранится в `soundcloud-session.json` рядом с рабочим
`config.json`, с правами `0600`. Путь меняется через `soundcloud.web_token_file`
или `QUASAR_SOUNDCLOUD_WEB_TOKEN_FILE`. Файл веб-сессии отделён от `token_file`
официального OAuth; браузерный токен не передаётся в официальный OAuth refresh.
Не отправляйте токен в чат и не добавляйте его в Git.

Для ручного управления есть команды:

```sh
sh /data/opt/quasar-bridge/app/start.sh -soundcloud-auth status
sh /data/opt/quasar-bridge/app/start.sh -soundcloud-auth logout
sh /data/opt/quasar-bridge/app/control.sh restart
```

`-soundcloud-auth login` читает токен из стандартного ввода, проверяет `/me` через
настроенный SOCKS5-прокси и сохраняет сессию. Не передавайте секрет аргументом
командной строки. При ручном входе или выходе перезапустите службу, чтобы изменение
применилось к работающему плееру. Выход оставляет публичный режим `web` и не
подменяет пользователя официальными реквизитами приложения.

Токен действует, пока его принимает SoundCloud. Автоматическое обновление
браузерной сессии не реализовано: при отказе авторизации повторите вход с новым
`oauth_token`. Если токен задан переменной `QUASAR_SOUNDCLOUD_WEB_ACCESS_TOKEN`,
для выхода сначала удалите её из `runtime.env`.

### Лайки и личная библиотека

После входа доступны лайки (они же избранное SoundCloud), свои загруженные треки,
собственные и сохранённые плейлисты. Например:

- «Алиса, включи мои лайки на SoundCloud».
- «Алиса, включи мой плейлист Осень на SoundCloud».
- «Алиса, включи мои треки на SoundCloud».
- «Алиса, покажи мои плейлисты на SoundCloud».
- Во время своей очереди SoundCloud: «мне нравится», «убери лайк».

Личный плейлист ищется в библиотеке своего аккаунта; чужой публичный плейлист с
таким же именем не подставляется. Воспроизведение использует ту же штатную очередь,
метаданные, обложки и переключения. Закрытые записи доступны лишь в пределах
разрешений аккаунта; предпрослушивания и заблокированные полные потоки пропускаются.

Для воспроизведения нужен поддерживаемый полный AAC/HLS-поток. Треки, доступные
только через DRM (`cbc-encrypted-hls`/FairPlay или `ctr-encrypted-hls`), сейчас не
поддерживаются: авторизация аккаунта не добавляет обработку DRM-лицензий в Bridge.
Если лайки есть, но все их потоки недоступны или не поддерживаются, колонка
сообщает об этом отдельно от действительно пустого избранного. В смешанном списке
используются доступные треки.

SoundCloud может потребовать браузерное подтверждение или CAPTCHA при изменении
лайков. В этом случае Bridge сообщает об отказе и не выдаёт его за успешное
добавление в избранное. Чтение библиотеки не означает гарантированного разрешения
на изменения; ограничения SoundCloud не обходятся.

### Где получить client ID и client secret

Для публичного режима `api: web` эти реквизиты не нужны. Для официального API
зарегистрируйте собственное приложение SoundCloud. По состоянию на 3 ноября
2026 года SoundCloud требует подписку **Artist Pro** для регистрации API-приложений.
Порядок и условия могут меняться: см. [получение API-реквизитов](https://developers.soundcloud.com/docs/api/register-app).

1. Войдите в свой аккаунт SoundCloud и откройте
   [Your Apps](https://soundcloud.com/you/apps/).
2. Создайте приложение: укажите название, описание интеграции и адрес сайта,
   примите условия API. Например, в описании можно указать воспроизведение музыки
   на собственной колонке через Quasar Bridge.
3. Скопируйте **Client ID** и **Client Secret** из реквизитов приложения.
   Client Secret — секрет приложения, а не пароль аккаунта SoundCloud.
4. Для пользовательского OAuth также настройте **Redirect URI** — адрес своего
   обработчика возврата после входа. Он должен совпадать с адресом, используемым
   при авторизации и обмене кода.

SoundCloud также предлагает официальный CLI регистрации; ссылка на него есть
в инструкции выше. Для Bridge достаточно браузерного варианта: устанавливать
этот CLI на колонку не требуется.

### Официальный каталог без входа пользователя

Для публичного поиска и воспроизведения достаточно пары приложения; личные
операции требуют отдельного согласия пользователя. Это разные OAuth-потоки:
`client_credentials` и Authorization Code с PKCE соответственно.
[Официальное описание авторизации](https://developers.soundcloud.com/docs/api/guide#authentication).

Добавьте в `config.json`:

```json
"soundcloud": {
  "enabled": true,
  "api": "official",
  "token_file": "/data/opt/quasar-bridge/soundcloud-tokens.json"
}
```

На колонке добавьте в `/data/opt/quasar-bridge/runtime.env` строки, подставив
собственные значения:

```sh
QUASAR_SOUNDCLOUD_CLIENT_ID="YOUR_CLIENT_ID"
QUASAR_SOUNDCLOUD_CLIENT_SECRET="YOUR_CLIENT_SECRET"
```

Сохраните существующие `default`, `compare_yandex`, `base_url` и остальные
нужные параметры блока. Значения в `runtime.env` являются shell-строками:
символы `$`, `"`, обратную косую черту и обратную кавычку внутри значения нужно
экранировать обратной косой чертой. Ограничьте доступ и перезапустите Bridge:

```sh
chmod 600 /data/opt/quasar-bridge/runtime.env
sh /data/opt/quasar-bridge/app/control.sh restart
```

Bridge сам получает токен приложения при первом запросе, используя HTTP Basic
на `https://secure.soundcloud.com/oauth/token`. Вручную заполнять `access_token`
для этого режима не нужно. `token_file` сохраняет полученные токены и позволяет
использовать их после перезапуска. Родительский каталог файла должен существовать
и быть доступен процессу Bridge для записи.

### Пользовательские access_token и refresh_token

Этот раздел относится к официальному OAuth своего приложения. Для входа через
браузерную сессию используйте способ выше и отдельный `web_token_file`.

Для чтения личных отметок «Нравится» и их изменения получите токены **своего
пользователя**, а не токен `client_credentials`. Встроенного браузерного OAuth-входа
и обработчика Redirect URI в Bridge пока нет. Первичную авторизацию выполняйте
на компьютере своим OAuth-клиентом или обработчиком по процедуре ниже; установщик
Bridge не выполняет первичный обмен кода официального OAuth.

1. Создайте случайный `code_verifier` длиной 43–128 символов, вычислите
   `code_challenge = BASE64URL(SHA256(code_verifier))` и создайте случайный `state`.
   Сохраните verifier и state до завершения входа. Например, на компьютере
   с OpenSSL:

   ```sh
   sc_verifier=$(openssl rand -hex 32)
   sc_challenge=$(printf '%s' "$sc_verifier" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')
   sc_state=$(openssl rand -hex 24)
   ```

2. Откройте в браузере URL по следующему шаблону. Подставьте Client ID,
   зарегистрированный Redirect URI, challenge и state; значения параметров
   должны быть URL-кодированы:

   ```text
   https://secure.soundcloud.com/authorize?client_id=YOUR_CLIENT_ID&redirect_uri=YOUR_URL_ENCODED_REDIRECT_URI&response_type=code&code_challenge=YOUR_CODE_CHALLENGE&code_challenge_method=S256&state=YOUR_STATE
   ```

3. Войдите в аккаунт и разрешите доступ. На своём Redirect URI получите `code` и
   проверьте, что возвращённый `state` точно равен сохранённому. При несовпадении
   прекратите обмен. Обменяйте код на токены с исходным verifier:

   ```sh
   curl --fail-with-body --request POST 'https://secure.soundcloud.com/oauth/token' \
     --header 'Content-Type: application/x-www-form-urlencoded' \
     --data-urlencode "grant_type=authorization_code" \
     --data-urlencode "client_id=$sc_client_id" \
     --data-urlencode "client_secret=$sc_client_secret" \
     --data-urlencode "redirect_uri=$sc_redirect_uri" \
     --data-urlencode "code=$sc_code" \
     --data-urlencode "code_verifier=$sc_verifier"
   ```

   Перед командой задайте `sc_client_id`, `sc_client_secret`, `sc_redirect_uri`
   и `sc_code` в своей оболочке. Redirect URI передаётся исходным, без отдельного
   URL-кодирования: это делает `--data-urlencode`.

Параметры PKCE и обмена описаны в
[официальном руководстве OAuth](https://developers.soundcloud.com/docs/api/guide#authentication).
Токен доступа действует примерно час; refresh token используется однократно и
заменяется новым при обновлении. Параллельное использование одного refresh token
несколькими экземплярами Bridge приведёт к конфликтам.

### Как передать пользовательские токены в Bridge

Оставьте `api: official`, Client ID и Client Secret, как в примере выше.
Из ответа OAuth возьмите `access_token` и `refresh_token`. Создайте на колонке
файл `/data/opt/quasar-bridge/soundcloud-tokens.json` с содержимым:

```json
{
  "access_token": "YOUR_USER_ACCESS_TOKEN",
  "refresh_token": "YOUR_USER_REFRESH_TOKEN",
  "user_authorized": true
}
```

`user_authorized: true` — поле формата Bridge: оно указывает, что файл содержит
результат пользовательской авторизации. Не ставьте его для токенов приложения.
Приведённый файл не задаёт срок истечения; Bridge использует токен до отказа API,
затем обновляет его и сохраняет новый срок и новую пару токенов автоматически.

```sh
chmod 600 /data/opt/quasar-bridge/soundcloud-tokens.json
sh /data/opt/quasar-bridge/app/control.sh restart
```

При таком способе не задавайте одновременно `access_token`/`refresh_token` в
`config.json` или `QUASAR_SOUNDCLOUD_ACCESS_TOKEN`/`QUASAR_SOUNDCLOUD_REFRESH_TOKEN`
в `runtime.env`: они имеют приоритет над файлом и после перезапуска могут вернуть
уже использованный refresh token. Client ID и Client Secret в `runtime.env`
оставьте — они нужны для обновления. Пароль SoundCloud, cookies браузера и токены
веб-сайта для этих настроек не используются.

Треки могут быть закрытыми, заблокированными в регионе, доступными только для
предпрослушивания или недоступными для потоковой передачи. Провайдер отфильтровывает
недоступные полные потоки и сообщает об ошибке, если воспроизводимых вариантов не
осталось. Он не обходит ограничения доступа, не перекодирует аудио и не сохраняет
загруженную музыку. URL ретранслятора непрозрачны и временны; они не раскрывают
подписанные URL медиаданных SoundCloud и учётные данные OAuth.
