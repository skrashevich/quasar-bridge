# Подробное руководство по Quasar Bridge

[Вернуться к README](../README.md). Здесь собраны полные инструкции по
установке на отдельный сервер и на колонку без менеджеров пакетов, настройке и диагностике.

Команды, если не указано иное, выполняются из корня репозитория.

Go-сервер для выборочной обработки запросов Яндекс Станции через нативный
WebSocket-протокол Quasar/Uniproxy:

- умный дом — через Home Assistant, если он подключён, иначе через Яндекс;
- сложные вопросы и распознанные отказы Алисы — через свою LLM;
- музыка, погода, таймеры и другие обычные запросы — через Яндекс.

Распознавание речи (ASR) и озвучивание (TTS) остаются в Яндексе. Даже запрос,
обрабатываемый локально, использует облачный речевой тракт. Схемы протокола:
[skrashevich/quasar-go-genproto](https://github.com/skrashevich/quasar-go-genproto).

## Что потребуется

- Сервер с Go **1.27.3+**, Git и OpenSSL; Python 3 — для подготовки конфигурации
  колонки и проверки публикуемого дерева. Рабочий сервер можно запустить на отдельном Linux-хосте или на самой колонке из готового архива.
- Уже полученный root и SSH-доступ к колонке. Этот проект не получает root
  и не устанавливает изменённую прошивку.
- Доступ сервера к Yandex Uniproxy и API LLM; Home Assistant MCP подключается по желанию.
- Доступ колонки к выбранному TCP-порту Go-сервера. Для DNS-имени сервера
  требуется разрешение этого имени и на колонке, и на машине проверки.
- OpenAI-совместимый API для режима `hybrid`. Совместимый HA MCP нужен только
  для локального управления домом. Режим `observe` работает без обоих API.

Все домены `*.example.invalid` ниже — заменяемые примеры, не готовые endpoints.
`SPEAKER_IP`, `ADMIN_IP`, `SERVER_IP` также нужно заменить своими значениями
в локальной конфигурации. Реальные адреса и секреты в репозиторий не добавляются.

## 1. Получить и собрать проект

```sh
git clone git@github.com:skrashevich/quasar-bridge.git
cd quasar-bridge
go version
go mod download
go build -trimpath -o bin/quasar-bridge ./cmd/quasar-bridge
```

Это сборка для текущей машины. Например, для Linux amd64 с другой машины:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -o bin/quasar-bridge-linux-amd64 ./cmd/quasar-bridge
```

`-trimpath` убирает локальные пути разработчика из бинарника. Для Linux arm64
используйте `GOARCH=arm64`. Для установки на колонку с AirPlay собирайте
законченный архив командой `python3 scripts/build-speaker-package.py --arch arm64`
(`--arch armv7` для 32-битной колонки): она также встраивает PCM-модули в
единственный исполняемый файл.

## 2. Проверить сервер в прозрачном режиме

Начните с `observe`: сервер пересылает трафик в Яндекс без локальной маршрутизации.
На этом шаге колонка ещё не перенастраивается.

```sh
umask 077
cp config.observe.example.json config.json
sh scripts/create-cert.sh certs DNS:localhost
./bin/quasar-bridge -config config.json
```

В другом терминале из каталога проекта:

```sh
curl --fail --cacert certs/ca.pem https://localhost:8443/healthz
```

Ожидается JSON со `status: "ok"` и `mode: "observe"`. Это проверка HTTP/TLS
Go-сервера, а не проверка колонки, LLM или HA. Остановите процесс через Ctrl+C
перед дальнейшим редактированием настроек.

Скрипт сертификатов не перезаписывает существующие файлы. Если каталог `certs`
уже существует, используйте его подходящий сертификат либо другой каталог.

## 3. Подключить LLM и Home Assistant

### API LLM

Скопируйте основной пример и откройте локальные файлы настроек:

```sh
cp config.example.json config.json
cp runtime.env.example runtime.env
chmod 600 config.json runtime.env
```

В `config.json` задайте:

- `mode`: `hybrid`;
- `llm_base_url`: базовый URL API **с `/v1`, без `/chat/completions` или `/responses`**;
- `llm_model`: точный идентификатор доступной модели;
- `home_warm_area`: при необходимости имя области HA, например `Кабинет`.

Если API требует ключ, запишите его в `QUASAR_LLM_API_KEY` в `runtime.env`.
Встроенная пара логин/пароль в URL не поддерживается.

Интерактивный установщик запрашивает доступные модели у выбранного провайдера
через `GET /models` и предлагает выбрать номер из списка. Сначала указываются
адрес и ключ API, для ChatGPT выполняется вход в браузере. Выбранный
идентификатор сохраняется в `QUASAR_LLM_MODEL`. При ошибке API или пустом
списке можно повторить настройку подключения либо отменить установку.

Для Chat Completions установщик также подбирает совместимые параметры запроса.
Сначала он проверяет стандартный набор; при HTTP 400/422 пробует убрать
отклонённое поле. Если сервер не указывает поле, по очереди убираются
`chat_template_kwargs`, `temperature`, `response_format`, `reasoning_effort`,
а `max_tokens` заменяется на `max_completion_tokens` или убирается совсем.
Каждый вариант должен вернуть обычный ответ и корректный JSON-объект.
Подбор ограничен десятью вариантами и двумя минутами. Ошибки авторизации,
квоты, доступности модели, региона и сети не исправляются перебором.

Рабочий объект сохраняется в `QUASAR_LLM_CHAT_PARAMETERS` в `runtime.env`
и переопределяет весь `llm_chat_parameters` из `config.json`.
Например, `{"chat_template_kwargs":null}` убирает это поле из запросов.
При явной настройке нового подключения подбор начинается со стандартных
параметров. Обновление с сохранением настроек их не меняет; отмена установки
восстанавливает прежние `config.json` и `runtime.env`.

Для обычных API-провайдеров установщик показывает HTTP-код и тело ошибки
LLM-сервера, включая неудачные
попытки, после которых удалось подобрать рабочий вариант. Ответы размером
до 2 МиБ выводятся полностью; превышение лимита или обрыв чтения помечаются
явно. Это действует также для получения моделей и проверки подключений.
Для Responses и ChatGPT подбор параметров не запускается. Вход через подписку
ChatGPT сохраняет прежний формат диагностики авторизации.

Подбор можно запустить отдельно, без записи настроек:

```sh
sh /data/opt/quasar-bridge/app/start.sh -probe-llm-compat
```

Команда использует выбранную модель, выводит рабочий JSON-объект в stdout,
а ответы сервера при ошибках — в stderr.

Для самостоятельной настройки список можно получить без генерации ответа:

```sh
quasar-bridge -config config.json -list-models
```

Команда использует тот же ключ или аккаунт ChatGPT, что и ответы LLM.
Она выводит по одной модели на строку: идентификатор и подпись, разделённые
табуляцией. Подпись заключена в кавычки. `llm_model` для этой команды и
`-chatgpt-auth` можно оставить пустым; обычный запуск и `-check-config`
по-прежнему требуют выбранную модель в режиме `hybrid`.

По умолчанию (`llm_api: "chat_completions"`) клиент делает
`POST /chat/completions` с `stream=false`, `temperature=0`,
`max_tokens=1024` и `chat_template_kwargs.enable_thinking=false`.
Для классификации и планирования действий он также передаёт
`response_format={"type":"json_object"}`. Сервер API должен принимать эти
параметры и возвращать `choices[0].message.content`.

Параметры запроса можно явно заменить через `llm_chat_parameters`.
Значение `null` удаляет поле из запроса, остальные значения заменяют его
целиком. Допускаются `temperature`, `max_tokens`, `max_completion_tokens`,
`response_format`, `chat_template_kwargs` и `reasoning_effort`. Поле
`response_format` применяется только к классификации и структурированному
планированию; обычные ответы остаются текстовыми. Модель, сообщения,
потоковый режим и настройки вызова инструментов задаёт мост. Непустой
`llm_chat_parameters` требует `llm_api: "chat_completions"` и перезапуска.
Формат и допустимые значения параметров зависят от выбранного API.

Для [OpenAI-совместимого endpoint Anthropic](https://platform.claude.com/docs/en/cli-sdks-libraries/libraries/openai-sdk)
отключите несовместимые параметры явно:

```json
{
  "llm_api": "chat_completions",
  "llm_base_url": "https://api.anthropic.com/v1",
  "llm_model": "claude-haiku-5-5",
  "llm_chat_parameters": {
    "temperature": null,
    "response_format": null,
    "chat_template_kwargs": null
  }
}
```

Ключ Anthropic задаётся через `QUASAR_LLM_API_KEY`. Параметры запроса задаются
явно и не зависят от имени хоста или модели.
JSON для классификации и планирования запрашивается инструкцией в промпте,
а результат проверяется мостом; серверная гарантия JSON-схемы здесь не
используется. Некорректный JSON приводит к штатной обработке ошибки,
а не к выполнению непроверенного плана.

Для [Responses API OpenAI](https://developers.openai.com/api/docs/guides/migrate-to-responses)
выберите `llm_api: "responses"`. Это позволяет использовать reasoning-модели
с локальными function tools, в том числе настроенными MCP-серверами:

```json
{
  "llm_base_url": "https://api.openai.com/v1",
  "llm_model": "your-reasoning-model",
  "llm_api": "responses",
  "llm_reasoning_effort": "low",
  "llm_max_output_tokens": 4096,
  "llm_hosted_tools": ["web_search", "code_interpreter"]
}
```

Это фрагмент настроек для добавления в `config.json`. Ключ по-прежнему
передаётся через `QUASAR_LLM_API_KEY`. Клиент отправляет `POST /responses`
с `stream=false` и `store=false`, без `temperature`, `max_tokens` и
`chat_template_kwargs`. Для классификации и планирования JSON-режим задаётся
через `text.format`. Контекст и результаты локальных инструментов передаются
в `input`; reasoning и другие элементы ответа сохраняются между вызовами
инструментов в рамках одного запроса.

`llm_reasoning_effort` необязателен: пустое значение оставляет выбор API.
Допускаются `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`;
конкретная модель может поддерживать только часть этих значений.
`llm_max_output_tokens` — положительный лимит Responses, по умолчанию 4096,
включающий reasoning-токены и текст ответа. При исчерпании лимита частичный
ответ отклоняется; при необходимости увеличьте бюджет. Эти параметры
не меняют `max_tokens=1024` режима Chat Completions.

`llm_hosted_tools` по умолчанию пуст. Можно включить
[веб-поиск](https://developers.openai.com/api/docs/guides/tools-web-search)
(`web_search`) и
[вычисления](https://developers.openai.com/api/docs/guides/tools-code-interpreter)
(`code_interpreter`, контейнер `auto`); их исполняет OpenAI.
Они работают и без `assistant_tools.enabled`. Для локальных инструментов
web/history/time/MCP требуется `assistant_tools.enabled: true`.
Hosted-инструменты отключены при классификации и структурированном
планировании, после доступа к приватной истории и в финальном раунде агента
при исчерпании его лимита инструментов. `llm_reasoning_effort` и непустой
`llm_hosted_tools` требуют режима `responses`.

Лимиты `assistant_tools.max_calls` и `max_rounds` учитывают локальные
function tools. Внутренние вызовы hosted-инструментов выполняются на стороне
провайдера в рамках одного HTTP-запроса и ограничены его правилами и общим
таймаутом запроса.

Оба режима ограничивают прямой запрос LLM 60 секундами. Изменение этих
настроек требует перезапуска моста; `SIGHUP` не пересоздаёт клиент LLM.
Один текстовый endpoint `/completions` не поддерживается.

Для [Responses API OpenRouter](https://openrouter.ai/docs/api_reference/responses/overview)
проверена следующая конфигурация:

```json
{
  "llm_api": "responses",
  "llm_base_url": "https://openrouter.ai/api/v1",
  "llm_model": "openrouter/free",
  "llm_max_output_tokens": 4096
}
```

Ключ OpenRouter задаётся через `QUASAR_LLM_API_KEY`. Маршрутизатор
`openrouter/free` выбирает доступную бесплатную модель для каждого запроса;
конкретная модель может меняться и между вызовами инструментов.
Проверены текст, JSON-режим, история диалога, `llm_reasoning_effort: "low"`
и локальные function tools. Hosted-инструменты OpenRouter в этот прогон
не входили. [Результаты проверки](validation.md#responses-api-и-openrouter).

### Обращения к модели в начале фразы

`llm_strip_prefixes` — список служебных обращений перед вопросом к нейросети.
Bridge убирает их перед передачей запроса в модель: некоторые модели понимают
«спроси у нейросети, который час» как просьбу обратиться к другой системе.
Исходная фраза сохраняется в истории диалога. При следующих запросах и повторе
предыдущие пользовательские сообщения тоже очищаются в копии контекста для
модели; ответы помощника не меняются.

По умолчанию включены: `спроси у нейросети`, `спроси нейросеть`,
`спроси у своей модели`, `спроси свою модель`, `спроси модель`.
Свой список заменяет значения по умолчанию, `[]` отключает срезание.
Регистр не важен; обращение распознаётся только в начале фразы, в том числе
после «Алиса,», и только целиком: «спроси модельный ряд» не меняется.
При совпадении нескольких обращений выбирается самое длинное.

После обращения убираются пробелы и один разделитель (`:`, `,`, `;`, `—`;
точка или восклицательный знак — если за ними пробел или конец фразы).
Пунктуация самого вопроса сохраняется: «спроси нейросеть: -2 в третьей степени»
даёт «-2 в третьей степени», «спроси нейросеть: .gitignore» — «.gitignore».
Если вопроса после обращения нет, исходный текст не меняется.
Отдельная команда «спроси нейросеть» по-прежнему повторяет предыдущий вопрос.

```json
{
  "llm_strip_prefixes": ["спроси нейросеть", "спроси у нейросети"]
}
```

Срезание выполняется после выбора маршрута для `llm` и `home`, включая
ответы с инструментами и повтор по команде «используй нейросеть».
Настройка не выбирает маршрут и не изменяет сохранённые правила маршрутизации.
Встроенное правило `complex_queries` содержит обращения из списка по умолчанию.
Если в конфигурации уже задан `routing.rules`, новые варианты обращений нужно
добавить в нужное правило самостоятельно; это относится и к собственным префиксам.
Настройку можно прочитать и изменить голосовыми инструментами конфигурации.
Изменение `llm_strip_prefixes` требует перезапуска Bridge.

### Подписка ChatGPT/Codex

Режим `llm_api: "chatgpt"` использует план ChatGPT через
[Sign in with ChatGPT для локальных приложений](https://developers.openai.com/siwc/token-sharing-open-source).
Доступность зависит от аккаунта, рабочего пространства и разрешения использовать
план в приложении. Расход учитывается в лимитах подписки; отдельный API-ключ
не нужен. `QUASAR_LLM_API_KEY` в этом режиме игнорируется. Доступ к истории
чатов ChatGPT этот вход не предоставляет.

При новой установке введите `chatgpt` вместо адреса API. Установщик предложит
войти в браузере, загрузит доступные этому аккаунту модели и попросит выбрать
номер. При ручной настройке существующей установки задайте в `config.json`
следующие поля либо используйте
[config.chatgpt.example.json](../config.chatgpt.example.json):

```json
{
  "mode": "hybrid",
  "llm_api": "chatgpt",
  "llm_base_url": "https://api.openai.com/v1",
  "llm_model": "your-account-model",
  "llm_chatgpt_auth_file": "/data/opt/quasar-bridge/chatgpt-auth.json",
  "llm_reasoning_effort": "low"
}
```

`llm_base_url` можно не указывать: выбирается `https://api.openai.com/v1`.
Другие адреса запрещены, чтобы токен подписки не попал стороннему провайдеру.
Если в `runtime.env` есть переопределения `QUASAR_LLM_API`,
`QUASAR_LLM_BASE_URL` или `QUASAR_LLM_MODEL`, измените их тоже: окружение
имеет приоритет над JSON. Модель должна быть доступна вашему аккаунту.
Точный идентификатор можно узнать командой `chatgpt-models` после входа.

Для входа на колонке **на компьютере** откройте SSH-туннель и оставьте его работать:

```sh
ssh -N -L 1455:127.0.0.1:1455 -p 2222 root@SPEAKER_IP
```

В другом терминале выполните:

```sh
ssh -t -p 2222 root@SPEAKER_IP /data/opt/quasar-bridge/app/control.sh chatgpt-login
```

Откройте напечатанную ссылку в браузере компьютера, войдите в ChatGPT и
разрешите Quasar Bridge использовать план. Обратный вызов браузера пройдёт
через туннель на колонку. Вход ожидается до 10 минут. Если локальный порт
1455 занят Codex, завершите его текущую процедуру входа либо выберите другой
порт: туннель и `-chatgpt-login-listen` должны указывать один и тот же порт.
Сам сервис Quasar Bridge не нужно останавливать для повторного входа.

После входа проверьте доступные модели, замените `your-account-model`
на нужный идентификатор, проверьте подключение и перезапустите сервис:

```sh
ssh -p 2222 root@SPEAKER_IP /data/opt/quasar-bridge/app/control.sh chatgpt-models
ssh -p 2222 root@SPEAKER_IP /data/opt/quasar-bridge/app/control.sh check-backends
ssh -p 2222 root@SPEAKER_IP /data/opt/quasar-bridge/app/control.sh restart
```

Состояние входа показывает `control.sh chatgpt-status`. Выход:
`control.sh chatgpt-logout`; он отзывает обновляемую сессию и удаляет локальные
токены, сохраняя регистрацию для повторного входа. Если удалённый отзыв
не подтверждён из-за сети, команда сообщает об этом; отключить приложение
можно также в настройках ChatGPT.

При запуске обычного бинарника доступны те же команды:

```sh
quasar-bridge -config config.json -chatgpt-auth login
quasar-bridge -config config.json -chatgpt-auth status
quasar-bridge -config config.json -chatgpt-auth models
quasar-bridge -config config.json -chatgpt-auth logout
```

JSON-конфигурация должна существовать и проходить проверку. Если файл учётных
данных не задан, используется каталог конфигурации ОС:
`quasar-bridge/chatgpt.json` внутри `os.UserConfigDir()`. Для колонки укажите
постоянный путь в `/data`. Файл создаётся атомарно с правами `0600`.
Токен обновляется автоматически, обновления сериализуются между процессами.
Не публикуйте файл и не добавляйте его в репозиторий. Для другого аккаунта
или рабочего пространства выберите другой `llm_chatgpt_auth_file` и выполните
вход; переключение файла в конфигурации требует перезапуска сервиса.
Кеш `~/.codex/auth.json` к этому формату не подходит: Bridge использует
собственную регистрацию приложения и не меняет сессию Codex.

По [ограничениям режима подписки](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)
запросы используют `store=false`, `stream=true` и передают контекст в каждом
запросе. Bridge принимает результат только после `response.completed`:
обрыв потока или ошибка не приводят к выполнению частичных вызовов инструментов.
История диалога, локальные инструменты и подключённые MCP работают через
function tools. Для классификации и планирования JSON запрашивается промптом
и проверяется мостом. `llm_chat_parameters` не поддерживается;
`llm_max_output_tokens` не передаётся, поскольку этот параметр запрещён
для подписки. Общий таймаут прямого запроса — 60 секунд. Из hosted-инструментов
можно указать только `web_search`, если он доступен модели и аккаунту;
`code_interpreter` отклоняется при проверке конфигурации.

При исчерпании лимита Bridge сообщает ошибку; платный API автоматически
не подключается. Проверить расход и разрешения приложения можно в
[ChatGPT → Settings → Usage](https://chatgpt.com/settings/usage).
Ошибки доступа и недоступные модели нужно проверить для выбранного аккаунта;
сам факт наличия подписки не гарантирует доступ к каждой модели.

### Home Assistant MCP

Этот раздел необязателен. Для работы только с LLM и Яндексом оставьте
`QUASAR_HOME_MCP_URL` пустым в `runtime.env`:

```sh
QUASAR_HOME_MCP_URL=
```

В `hybrid` по-прежнему задайте `llm_base_url` и `llm_model`. Пустой или
отсутствующий MCP URL отключает интеграцию: HA-клиент и фоновый прогрев не
запускаются, а любой выбор `home` (правило, маршрут по умолчанию или классификатор)
передаётся в Яндекс. Удалять домашние правила из конфига не требуется.
`-route` показывает фактический маршрут `yandex` и `source: "home_disabled"`,
сохраняя имя совпавшего правила; `/healthz` содержит `home_assistant_enabled: false`.
LLM, её инструменты, журнал и контекст диалога продолжают работать.
Подключение или отключение HA требует изменения окружения и перезапуска сервиса.
Непустой MCP URL должен быть корректным HTTP/HTTPS URL: ошибка в нём не отключает
интеграцию молча. Если HA настроен, но недоступен, команда не повторяется в облаке.

Чтобы подключить HA, задайте `QUASAR_HOME_MCP_URL` по инструкции ниже.

Нужен HTTP MCP-сервер с инструментами **`ha_*`**, например
[homeassistant-ai/ha-mcp](https://github.com/homeassistant-ai/ha-mcp).
Установите его по инструкции соответствующей версии проекта и получите
HTTP endpoint с доступом из сети Go-сервера. Для текущего клиента подходит
режим Secret URL / capability URL без интерактивного входа.

Обязательные инструменты:

| Инструмент | Для чего используется |
| --- | --- |
| `ha_get_skill_guide` | Правила работы и `references/device-control.md` |
| `ha_search` | Сущности, состояния, области, псевдонимы и состав групп |
| `ha_get_entity_exposure` | Разрешение сущности для Assist |
| `ha_call_service` | Выполнение команд |
| `ha_get_state` | Независимое чтение состояния после команды |

Клиент посылает MCP JSON-RPC через HTTP POST, принимает JSON и SSE,
передаёт `Mcp-Session-Id`, если сервер его выдал. Он не запускает stdio-сервер
и не выполняет OAuth-вход; отдельный Bearer-заголовок для MCP сейчас не задаётся.
Штатный HA MCP с другим набором инструментов, например только `HassTurnOn`,
не является совместимой заменой этого контракта.

Полный URL, включая секретный путь, задайте в `runtime.env`:

```sh
QUASAR_HOME_MCP_URL='https://home.example.invalid/mcp'
QUASAR_LLM_API_KEY=''
```

Подставьте свой endpoint и ключ; URL из примера не работает. Если URL сам
является секретом, храните его как токен и не публикуйте в выводе диагностики.
Доступ к самому Home Assistant настраивается на стороне HA MCP.

В HA разрешите нужные устройства для **Assist** и проверьте их названия,
области и псевдонимы. Quasar Bridge использует `conversation=true` из
`ha_get_entity_exposure`. Устройство без этого разрешения не попадёт в выборку.
Имя `home_warm_area` лишь подготавливает кеш и **не задаёт комнату по умолчанию**
для команд: комнату лучше называть в запросе.

### Проверка обработчиков без колонки

Загрузите окружение в текущую оболочку и проверьте API:

```sh
set -a
. ./runtime.env
set +a
./bin/quasar-bridge -config config.json -check-backends
./bin/quasar-bridge -config config.json \
  -query 'Спроси нейросеть: объясни, почему небо голубое'
./bin/quasar-bridge -config config.json \
  -query 'Горит ли свет в кабинете?'
```

`-check-backends` запрашивает короткий ответ LLM и, если HA подключён, список его сущностей.
Без HA результат — `LLM: ok; Home Assistant: disabled`; отсутствие интеграции не считается ошибкой.
Он не доказывает возможность физического управления или работу микрофона.
`-query` возвращает JSON с `Route` и `Answer`.
Для аудиокоманд он создаёт тестовый контекст колонки и возвращает запланированные
команды плееру в `playback` с отметкой `playback_simulated: true`. Сайт загружается
и аудиоссылки ищутся обычным обработчиком; звук на колонке не запускается.
Остальные команды управления в нём **реально выполняются**. Для `yandex` эта команда
лишь показывает выбранный маршрут: CLI не создаёт сессию колонки, не ставит
таймер и не получает облачный ответ. В режиме `observe` локальные обработчики
на WebSocket не включаются, даже если отдельная проверка `-query` работает.

## 4. Открыть доступ колонки к серверу

Выберите реальное DNS-имя сервера и создайте отдельный сертификат для него:

```sh
BRIDGE_HOST='bridge.example.invalid'  # замените своим DNS-именем
BRIDGE_URL="wss://${BRIDGE_HOST}:8443/uni.ws"
umask 077
mkdir -p private
sh scripts/create-cert.sh private/certs "DNS:${BRIDGE_HOST}"
```

Если в `BRIDGE_HOST` используется IP, вместо `DNS:` передайте `IP:`.
Имя/IP в `BRIDGE_URL` должно совпадать с SAN сертификата. В сертификат
можно передать один SAN; скрипт не добавляет адреса автоматически.

В `config.json` измените следующие поля (остальные параметры `hybrid` сохраните):

```json
{
  "listen": ":8443",
  "tls_cert": "private/certs/server.pem",
  "tls_key": "private/certs/server.key",
  "allowed_ips": ["SPEAKER_IP", "ADMIN_IP", "SERVER_IP"]
}
```

Этот фрагмент — не полный конфиг. Подставьте числовые IP вместо плейсхолдеров.
`listen: ":8443"` слушает сетевые интерфейсы; `allowed_ips` ограничивает
клиентов точными IPv4/IPv6-адресами, **без CIDR и DNS-имён**. Добавьте адреса
машин диагностики, включая сервер при обращении к его сетевому адресу.
Пустой список отключает фильтрацию. Firewall также должен пропускать TCP-порт
от колонки. Для исходящего WebSocket требуется доступ к Yandex Uniproxy.

Убедитесь, что активные `QUASAR_*` из окружения не перекрывают отредактированный
JSON. **В отдельном терминале**, из каталога проекта, загрузите окружение и
оставьте сервер работать в foreground:

```sh
set -a
. ./runtime.env
set +a
./bin/quasar-bridge -config config.json
```

В основном терминале, где заданы `BRIDGE_HOST` и `BRIDGE_URL`, проверьте endpoint:

```sh
curl --fail --cacert private/certs/ca.pem "https://${BRIDGE_HOST}:8443/healthz"
```

При проверке с другой машины скопируйте туда публичный CA и задайте
`BRIDGE_HOST` заново: переменные оболочки не переходят между терминалами.

Сертификат сервера действителен 90 дней, CA — 365 дней. Автоматического
продления нет. При замене CA понадобится обновить доверие на колонке;
приватный `ca.key` на колонку не переносится.

## 5. Направить rooted-колонку на Go-сервер

Ниже — процедура для firmware с конфигурацией
`/system/vendor/quasar/quasar.cfg` и CA bundle
`/system/vendor/quasar/ca-certificates.crt`. До выполнения проверьте пути
и структуру своей firmware. Сценарии применения предполагают возможность
`mount -o remount,rw /`; наличие root само по себе этого не гарантирует.

В основном терминале задайте свой SSH-адрес и порт. Здесь должны сохраняться
`BRIDGE_URL` и `BRIDGE_HOST` из предыдущего шага; сервер продолжает работать
в отдельном терминале:

```sh
SPEAKER_HOST='speaker.example.invalid'  # замените адресом или SSH-алиасом
SPEAKER_SSH_PORT=22                    # замените портом root SSH
STAGE='/data/opt/quasar-bridge-stage'
umask 077
mkdir -p private
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  'cat /system/vendor/quasar/quasar.cfg' > private/quasar.cfg.orig
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  'cat /system/vendor/quasar/ca-certificates.crt' > private/ca-certificates.crt.orig
```

Сохраните исходники и подготовьте изменённую копию **на своём компьютере**:

```sh
python3 - "$BRIDGE_URL" <<'PY'
import json
import sys
from pathlib import Path

source = Path('private/quasar.cfg.orig')
config = json.loads(source.read_text())
config['aliced']['uniProxyUrl'] = sys.argv[1]
config['aliced']['uniProxyQuicUrl'] = ''
Path('private/quasar.cfg.pilot').write_text(
    json.dumps(config, ensure_ascii=False, indent=2) + '\n'
)
PY
```

Изменяются только адрес голосового WebSocket и отключение QUIC-обхода.
Остальную конфигурацию сохраните: она может содержать данные аккаунта.
Подготовленные файлы находятся в игнорируемом каталоге `private/`.

Перенесите конфигурацию, **публичный** CA и скрипты через SSH. Этот способ
не требует SFTP на embedded-устройстве:

```sh
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" "mkdir -p '$STAGE'"
for name in apply-pilot.sh rollback-pilot.sh; do
  ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
    "cat > '$STAGE/$name'" < "scripts/$name"
done
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  "cat > '$STAGE/quasar.cfg.pilot'" < private/quasar.cfg.pilot
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  "cat > '$STAGE/bridge-ca.pem'" < private/certs/ca.pem
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  "sh '$STAGE/apply-pilot.sh' '$STAGE' && reboot"
```

Скрипт сохраняет исходный config и CA на колонке в
`/data/opt/quasar-bridge-backup` и возвращает корневую FS в read-only.
Повторное применение поверх отмеченного пилота отклоняется.

Для нестандартных путей предусмотрены `QUASAR_DEVICE_CONFIG`,
`QUASAR_DEVICE_CA_BUNDLE`, `QUASAR_DEVICE_BACKUP_DIR`. Передавайте одинаковые
значения удалённым скриптам применения и отката; локальный `export` не
переносит их в SSH автоматически. Команды чтения файлов выше тоже нужно
адаптировать к этим путям.

После перезагрузки проверьте три запроса на колонке:

| Запрос | Ожидаемый обработчик |
| --- | --- |
| «Алиса, какая завтра погода?» | Яндекс |
| «Алиса, спроси нейросеть: объясни, почему небо голубое» | Своя LLM |
| «Алиса, горит ли свет в кабинете?» | HA + своя LLM для ответа |

Физическое управление проверяйте на выбранном устройстве и сверяйте его
состояние в HA. Голосовое «готово» или HTTP 200 само по себе не подтверждает
изменение состояния.

## Запуск на самой колонке без менеджеров пакетов

Пошаговая установка готового архива, настройка LLM, переключение Алисы,
обновление и удаление описаны в [README](../README.md#установка).
Нужны root, SSH, Linux с `/proc` и BusyBox init, запускающий `/etc/init.d/S*`.
Основной Bridge для ARM64 и ARMv7 статический (`CGO_ENABLED=0`).
PCM-модули встроены в тот же бинарник. При использовании AirPlay библиотека
автоматически подготавливает нужный модуль в приватном кэше и загружает штатную ALSA. Архив не зависит от YAM и не устанавливает системные пакеты. Поддержку конкретной прошивки,
перезагрузку и голосовой тракт проверяйте на самой колонке.

### Проверенные сценарии установки

Проверено на реальных колонках с архивами из этой ветки, переданными по SSH:

| Модель | Первая установка в пустой каталог | Повторное обновление | Переход с YAM | Автозапуск после перезагрузки |
| --- | --- | --- | --- | --- |
| Станция 2, Linux 4.9.68 / BusyBox 1.31.1 | Да | Да | Да, со штатным каталогом и ссылкой `/data` | Да |
| MIDI, Linux 5.4.180 / BusyBox 1.36.1 | Да | Да | На этой колонке YAM не был установлен | Да |

Для проверки первой установки на Станции 2 рабочий каталог временно переносился
целиком и затем возвращался. Конфиги, ключи, backup подключения и firmware-конфиг
после проверок совпали с исходными по SHA-256. Переход с YAM сохранил работающий
демон YAM и оригинальный пакет в `yam-package.backup`. Проверки LLM и Home Assistant
на рабочей конфигурации Станции 2 прошли. Для чистых установок использовался
временный тестовый API; проверка голосовых ответов с выбранной моделью остаётся
отдельным шагом пользователя.

### Сборка архива для колонки

На компьютере нужны Go из `go.mod` и Python 3. Для сборки обоих вариантов:

```sh
python3 scripts/build-speaker-package.py --arch arm64
python3 scripts/build-speaker-package.py --arch armv7
# dist/quasar-bridge-linux-{arm64,armv7}.tar.gz и .tar.gz.sha256
```

Для записи версии в `VERSION` добавьте `--tag vMAJOR.MINOR.PATCH`.
Для сжатия бинарника установите UPX и добавьте `--upx`:

```sh
python3 scripts/build-speaker-package.py --arch arm64 --upx
python3 scripts/build-speaker-package.py --arch armv7 --upx
```

Сборщик использует `upx -6 --no-lzma`: обычный уровень сжатия без длительного
перебора `--ultra-brute`, с быстрым распаковщиком NRV, без более медленного LZMA.
Затем `upx -t` проверяет целостность; при ошибке новый архив не создаётся. Исходный файл,
переданный через `--binary`, не изменяется. Без `--upx` UPX не требуется.
Сжатие уменьшает размер на диске, но не гарантирует отсутствие накладных расходов:
при каждом запуске бинарник распаковывается, а потребление RAM на Linux может
увеличиться. Влияние на запуск и память конкретной колонки требует замеров.

Имена архивов постоянные, чтобы установщик мог скачать последний выпуск без JSON API GitHub.
`--binary PATH` упаковывает заранее собранный статический ELF соответствующей
архитектуры. Сборщик проверяет класс ELF и machine ID, но не определяет наличие
динамических зависимостей у переданного бинарника: используйте `CGO_ENABLED=0`.
PCM-модули собирает команда `station-pcm-package` из зависимости
`station-airplay` и встраивает их внутрь ELF после сжатия основного кода.
Исходников проигрывателя в Bridge нет. Для заранее собранных модулей доступны
`--pcm-armv7-binary PATH` и `--pcm-arm64-binary PATH`; это параметры сборки,
а не дополнительные файлы для установки. Переданный `--binary` сохраняется.
Архив содержит один исполняемый `bin/quasar-bridge`, скрипты, пример настроек,
`ARCH`, `VERSION`, `LICENSE`,
`NOTICE` и `THIRD_PARTY_NOTICES`. Список файлов явный: локальные конфиги,
ключи и журналы в архив не попадают.
CI проверяет установку в BusyBox и параллельно собирает архивы ARM64 и ARMv7
в отдельных заданиях с UPX 5.2.1 (версия и SHA-256 загрузки закреплены в workflow).
Проверки запускаются для pull request и push в `main`; новый запуск отменяет
устаревшие проверки той же ветки или PR. Релизные сборки автоматически не отменяются.
Общий архив исходников и `install.sh` готовятся один раз. Workflow
[standalone release](../.github/workflows/release.yml) запускается по тегу
`vMAJOR.MINOR.PATCH`: после успешных проверок публикует готовые артефакты CI без
повторной сборки: `install.sh`, архив исходников, оба архива для колонок и их SHA-256.
Перед публикацией загруженные файлы скачиваются обратно и
сравниваются с результатами сборки. Ручной запуск workflow выполняет проверки
и сборку без публикации. Пакеты YAM (`.yap`) больше не собираются.

### Ручная установка архива

Обычная установка выполняется одной командой с компьютера из README.
Компьютер скачивает архив, затем передаёт и запускает его по SSH. Это работает
и на свежей MIDI: её BusyBox wget не поддерживает HTTPS, а tar — флаг `-z`;
поэтому установщик использует отдельный `gzip` и запускается перед `S97quasar`.
Если на колонке уже есть HTTPS-клиент, тот же скачанный `install.sh` можно
запустить прямо на ней без аргумента SSH-адреса. Ниже — вариант для
локальной сборки, ограниченного доступа колонки к GitHub или установки конкретного выпуска.
На компьютере скачайте `.tar.gz` и `.tar.gz.sha256` из одного выпуска либо соберите их командами выше.
Для ARMv7 замените `arm64` на `armv7`:

```sh
# На компьютере, в каталоге с архивом:
shasum -a 256 -c quasar-bridge-linux-arm64.tar.gz.sha256
scp quasar-bridge-linux-arm64.tar.gz root@SPEAKER_IP:/data/
ssh root@SPEAKER_IP
```

После успешной проверки SHA-256, на колонке:

```sh
stage=$(mktemp -d /tmp/quasar-bridge-install.XXXXXX)
gzip -dc /data/quasar-bridge-linux-arm64.tar.gz | tar -xf - -C "$stage"
sh "$stage/setup.sh"
```

`setup.sh` запускает тот же интерактивный мастер, что и установщик из интернета.
Для установки без вопросов, с заранее подготовленным конфигом, используйте
`sh "$stage/install.sh"`. На первой такой установке будет создан конфиг `observe`;
подключение LLM и `control.sh apply` выполняются вручную.

Мастер хранит настройки нейросети в помеченном блоке `runtime.env`, который имеет
приоритет над JSON. При перенастройке заменяются настройки нейросети в этом блоке;
URL Home Assistant, прочие строки и существующий JSON сохраняются. По умолчанию URL Home Assistant
запрашивается только при первой установке, ввод виден. Чтобы изменить или отключить
подключение умного дома позже, отредактируйте `QUASAR_HOME_MCP_URL` в `runtime.env`
и выполните `control.sh restart`. Ключ API вводится без эха; Enter оставляет его
пустым. Если мастер отменён до успешной установки, прежние конфиги восстанавливаются.

Заголовки шагов, вопросы, успехи и ошибки выделяются в терминале.
При перенаправлении вывода и с `NO_COLOR=1` цвета отключаются.
Успешные служебные проверки показаны кратко, а при ошибке выводится вся диагностика.
Меню после ошибки позволяет изменить только нейросеть или URL Home Assistant,
повторить проверку либо отменить установку.
При запуске с компьютера команда туннеля для входа в ChatGPT уже содержит SSH-адрес,
порт и остальные параметры подключения из команды установки.

### Каталоги и управление службой

- `/data/opt/quasar-bridge/app` — установленная программа и скрипты.
- `/data/opt/quasar-bridge/app.previous` — предыдущая версия после обновления.
- `/data/opt/quasar-bridge/config.json`, `runtime.env` — настройки и секреты.
- `/data/opt/quasar-bridge/endpoint-backup.json` — исходные endpoint Алисы.
- `/data/opt/quasar-bridge/service.log` — stdout/stderr программы.
- `/etc/init.d/S96quasar-bridge` — собственный автозапуск, перед `S97quasar` на MIDI и `S99quasar` на других прошивках.

```sh
pkg=/data/opt/quasar-bridge/app
sh "$pkg/control.sh" check
sh "$pkg/control.sh" check-backends
sh "$pkg/control.sh" status
sh "$pkg/control.sh" logs
sh "$pkg/control.sh" restart
```

`stop` и `start` предназначены для временной остановки и запуска. `restart`
сначала проверяет конфиг, затем ждёт завершения прежнего процесса и готовности
нового. PID сверяется с `/proc/PID/exe`, чтобы не послать сигнал постороннему
процессу. Скрипт отказывается запускать второй bridge, если порт уже обслуживает
неуправляемый экземпляр. Это обычный фоновый процесс с init hook при загрузке;
автоматического перезапуска после аварии нет.

Файлы состояния имеют права `0600`, каталог — `0700`. `runtime.env` загружается
как shell-файл; значения со спецсимволами заключайте в кавычки. По умолчанию
`SSL_CERT_FILE=/system/vendor/quasar/ca-certificates.crt`, `GOMAXPROCS=1`,
`GOMEMLIMIT=64MiB`. Их можно переопределить в `runtime.env`.
Журнал при следующем запуске переносится в `service.log.1`, если превысил 1 МиБ;
между перезапусками его размер не ограничен. Для постоянной записи диалогов
используйте отдельные лимиты `conversation_log`.

Для иной раскладки задайте `QUASAR_DATA_DIR` и, при необходимости,
`QUASAR_INIT_DIR` при установке. Путь состояния должен быть абсолютным,
состоять из латинских букв, цифр, `/`, `.`, `_`, `-` и не содержать `..`-компонентов.
Установщик записывает путь состояния в init hook. При ручном вызове скриптов
передавайте тот же `QUASAR_DATA_DIR`; `QUASAR_INIT_DIR` нужен также при удалении.
Не переносите `QUASAR_DATA_DIR` только в `runtime.env`: файл ищется раньше.

### Подключение и возврат endpoint

```sh
sh /data/opt/quasar-bridge/app/control.sh apply
# Только после успешного apply:
reboot
```

`apply` требует работающий экземпляр и локальный `/healthz`, сохраняет прежние
`aliced.uniProxyUrl` и `uniProxyQuicUrl`, устанавливает
`ws://127.0.0.1:8443/uni.ws` и отключает QUIC-обход. Другие поля сохраняются.
Повторный `apply` не затирает backup. `rollback` возвращает только сохранённые
поля; посторонние изменения endpoint приводят к отказу для ручной проверки.
Обе команды временно открывают `/` на запись, если он был read-only, и
восстанавливают прежний режим. Для нестандартного firmware config задайте
`QUASAR_DEVICE_CONFIG` при **обоих** действиях.

До удаления выполните `rollback`, перезагрузите колонку и убедитесь, что Алиса
работает напрямую. Затем запускайте `uninstall.sh`. Он сохраняет пользовательские
данные и отказывается удалять программу при наличии backup endpoint.

### Переход с YAM

Новый установщик сохраняет прежний каталог `/data/opt/quasar-bridge`:
`config.json`, `runtime.env`, журналы и `endpoint-backup.json` переносить не нужно.
Он не обращается к API YAM и не управляет другими приложениями YAM.

Мастер распознаёт стандартный каталог
`/data/quazar/yam/data/plugins/quasar-bridge` и предлагает автоматический переход:
перемещает только этот пакет в `/data/opt/quasar-bridge/yam-package.backup`,
останавливает его процесс после проверки `/proc/PID/exe` и включает собственный
init hook. API YAM не вызывается; его демон и другие приложения не затрагиваются.
При ошибке установки каталог пакета возвращается на место; его запуск при необходимости
нужно восстановить в YAM. После успешного перехода не включайте старый пакет повторно.

Для нестандартного размещения до установки остановите старый экземпляр Quasar Bridge и отключите **его**
автозапуск в своей версии YAM. Универсальной команды для несовместимых версий
YAM нет. Проверьте `ps` и отсутствие ответа `/healthz` после остановки;
не завершайте процессы только по совпадению имени или вслепую по PID-файлу.
Если YAM больше не используется для других приложений, отдельно отключите
его startup hook, например ранее установленный `/etc/init.d/S98quasar-yam`.
Если другие приложения нужны, оставьте их запуск и отключите только bridge.

Сохраните старый пакет и каталог состояния для отката. После этого установите
новый архив. Если сохранённый endpoint уже указывает на локальный bridge,
повторный `apply` не нужен: проверьте новый процесс и перезагрузку. Если прежняя
установка не создала `endpoint-backup.json`, сначала восстановите исходный
endpoint по её резервной копии; не создавайте новую копию поверх локального URL.
Не удаляйте старую установку вместе с каталогом состояния.

## Состояние подписок

`GET /healthz` содержит `speaker_subscriptions` — последние явно переданные
состояния для каждого открытого соединения с колонкой:

```json
{
  "speaker_subscriptions": [
    {
      "connection": 1,
      "device_subscription": "none",
      "alice_pro_subscription": "active",
      "endpoints": []
    }
  ]
}
```

`device_subscription` принимает `none`, `yandex_subscription` или `unknown`.
Монитор читает `DeviceSubscriptionState` из `DeviceState`, а при его отсутствии —
из `EnvironmentState.Devices[].SpeakerDeviceState` с совпадающим идентификатором
устройства. Явное состояние в `DeviceState` имеет приоритет.

`alice_pro_subscription` относится отдельно к Алисе Про: `active`, `none` или
`unknown`. Источник — `AliceProCapability.State` собственного endpoint колонки;
состояния других колонок в том же окружении не меняют это поле.

`endpoints` содержит состояния `BrickCapability`: режим покупки колонки по
подписке и блокировку. Пустой список означает отсутствие полученных
Brick-состояний и не определяет наличие Алисы Про. Значение `subscription_unblocked`
говорит об отсутствии блокировки в переданном состоянии, а не подтверждает оплату.

Монитор пассивно читает проходящие сообщения: не обращается к биллингу и не
меняет блокировку колонки. Отсутствующие или повреждённые данные не стирают
предыдущее явное состояние. Новое соединение начинает со статусов `unknown`;
при смене идентичности устройства собственные статусы также сбрасываются.

## Журнал запросов и ответов

По умолчанию тексты **не записываются**. Для включения добавьте в `config.json`:

```json
"conversation_log": {
  "enabled": true,
  "path": "runtime/conversations.jsonl",
  "max_size_mb": 10,
  "max_backups": 3,
  "max_text_chars": 16000
}
```

Перечитайте конфиг через `SIGHUP` или `systemctl reload quasar-bridge`.
Это работает и для уже открытых соединений. Для выключения установите
`enabled: false` и перечитайте снова. Изменение параметров журнала и routing
проверяется до применения; ошибка файла/JSON сохраняет предыдущие настройки.
В `/healthz` есть `conversation_log_enabled` и счётчик ошибок записи
`conversation_log_failures`. Ошибка записи не прерывает ответ колонке.

Одна строка JSON — одно событие: `request` (TextInput/VoiceInput/SpeechInput),
`transcript` (финальное ASR), `route`, `cloud_response`, `response` или `cancel`.
В `response` записывается текст, успешно отправленный по WebSocket колонке;
это не подтверждение, что пользователь его услышал. `cloud_response` — ответ,
полученный из Яндекса, в том числе заменённый локальной моделью. Наличие пары
`cloud_response` и `response` с одинаковым текстом ожидаемо: это получение и
доставка одного ответа. Корреляция — поля `session` и хешированный `request`.
`text` содержит карточки, `speech` — текст озвучивания, `route` — выбранный
обработчик (до выбора маршрута в hybrid поле отсутствует), `elapsed_ms` — время от начала запроса. Промежуточное ASR, raw
protobuf/JSON, OAuth/HTTP-заголовки, URL с токенами и аудиофреймы не сохраняются.
Двоичные команды без текстового ответа не превращаются в выдуманный текст.
Диагностический `-query` не является запросом колонки и в этот журнал не попадает.

Файлы создаются с правами `0600`, новые каталоги — `0700`. Путь считается от
рабочего каталога процесса. При достижении лимита журнал становится `.1`, затем
`.2` и т. д.; хранится текущий файл плюс `max_backups` архивов. Длинный текст
обрезается по Unicode-символам с признаком `truncated: true`.
Тексты могут содержать личные данные, даже когда служебные токены исключены.
Журналы исключены из Git и пакета.

Для systemd задайте **`path: "/var/log/quasar-bridge/conversations.jsonl"`**:
обновлённый unit создаёт writable-каталог через `LogsDirectory=quasar-bridge`.
При обновлении старого unit добавьте также `LogsDirectoryMode=0700` и выполните
`systemctl daemon-reload` с перезапуском службы. Для пакета на колонке пример
использует `path: "conversations.jsonl"`, **1 МиБ × 3 файла** с учётом текущего,
чтобы ограничить расход flash. Не ставьте большой журнал на маленькую `/data`.

## Контекст последовательных вопросов

Локальная LLM получает предыдущие вопросы и ответы той же колонки. Например:
«О чём мы сегодня общались?» → «А вчера?» → «А сегодня?». Короткое уточнение
остаётся в локальном диалоге; поиск истории выполняется заново за указанную
в последней реплике дату. Классификатор также получает недавние реплики.

```json
{
  "dialogue_context": {
    "enabled": true,
    "ttl_seconds": 300,
    "max_turns": 6,
    "max_chars": 12000
  }
}
```

По умолчанию включено: до 6 пар «вопрос — ответ», до 12000 символов,
5 минут бездействия. Лимиты допускают 1–20 пар, 512–65536 символов и
30–86400 секунд. Изменение настроек требует перезапуска Go-сервера.
Контекст хранится в оперативной памяти и очищается при перезапуске или
фразе «Алиса, начни новый разговор». Он отделён от постоянного JSONL-журнала.

Ключом служит идентификатор устройства или установки из Quasar; без них
память ограничена одним WebSocket-соединением. При наличии идентификатора
переподключение колонки сохраняет контекст. На одной колонке эта память
общая для говорящих рядом людей; разделения по голосу нет.

Контекст применяется к разговорам с локальной LLM. Явные правила для нового
запроса сохраняют приоритет: музыка, погода и команды умного дома выбирают
свой маршрут и завершают прежнюю локальную тему. Прошлые команды не передаются
в планировщик физических действий. Если в контекст попала личная история,
веб-инструмент остаётся заблокированным до завершения, сброса или истечения контекста.
В памяти сохраняются финальные реплики; сырые результаты инструментов не копируются.

## Повтор предыдущего вопроса через нейросеть

После ответа скажите «Алиса, спроси нейросеть» или «Алиса, используй нейросеть».
Точная фраза без продолжения повторяет
предыдущий завершённый информационный вопрос в локальной LLM вместе
с сохранёнными репликами перед ним. Саму команду и прежний ответ на
повторяемый вопрос модель не получает: она отвечает на исходный вопрос заново.
После повторного ответа колонка снова слушает, если включён `listen_after_reply`;
во время ожидания и озвучивания ответа повторное прослушивание не запускается.

Для этой команды отдельно сохраняются завершённые текстовые ответы Алисы,
включая потоковые, и локальной модели. Это история в оперативной памяти,
а не поиск по JSONL-журналу: действуют лимиты `dialogue_context` по времени,
числу реплик и символов. Перезапуск или «начни новый разговор» очищает её.
История отделена по колонкам, но общая для людей, говорящих с одной колонкой.

Фраза с новым вопросом, например «спроси нейросеть, почему небо голубое»,
отправляет новый вопрос, а не повторяет предыдущий. Пустое дослушивание после
ответа не стирает сохранённый вопрос и не продлевает срок его хранения.

Перед повтором отдельно проверяется его допустимость. При отрицательном,
неопределённом ответе или ошибке проверки генерация не запускается.
Обычный повтор выполняется без инструментов и внешних действий. Для вопроса
о конфигурации Quasar Bridge доступно только локальное чтение актуальных
настроек и времени: запись, перезапуск, MCP и сетевые инструменты запрещены
самим сервером. Команды умного дома,
воспроизведения и ответы с исполнительными директивами не повторяются.


## Следующий вопрос после локального ответа

По умолчанию после озвученного локального ответа колонка снова слушает:
следующий вопрос можно задать без повторного обращения «Алиса».
Настройка `"listen_after_reply": true` действует и для обычного ответа,
и для финального ответа при `local_progress`. Промежуточное беззвучное
ожидание не включает прослушивание. Длительность ожидания следующего вопроса
определяет прошивка колонки.

Чтобы вернуть завершение диалога после ответа, добавьте в основной конфиг
`"listen_after_reply": false` и перезапустите Go-сервис. Ответы Яндекса
сохраняют собственное поведение. Беззвучный запуск музыки или управление
воспроизведением не включает прослушивание, чтобы не мешать аудио.

## Долгие локальные ответы и тайм-аут колонки

Некоторые прошивки ждут первоначальный ответ около 15 секунд. Если LLM или
Home Assistant отвечает дольше, включите серверное ожидание:

```json
{
  "local_progress": {
    "enabled": true,
    "after_ms": 2000,
    "interval_ms": 4000
  }
}
```

Добавьте этот блок в основной конфиг и **перезапустите** Go-сервис. На колонке:
`sh /data/opt/quasar-bridge/app/control.sh restart`. По умолчанию режим
выключен; `config.example.json` показывает включённый вариант.

После выбора локального маршрута сервер ждёт `after_ms`, затем при необходимости
начинает беззвучное ожидание. Пока обработчик работает, сервер передаёт потоковые
сообщения Quasar и тишину в одном непрерывном Ogg/Opus-потоке. Готовый ответ
добавляется в тот же поток; колонка завершает воспроизведение после его окончания.
Прошивочный тайм-аут менять не требуется. Пауза не ускоряет модель и не снимает
общий лимит обработки запроса.

`after_ms` допускает 100–10000 мс, `interval_ms` — 1000–10000 мс и задаёт частоту
промежуточных сообщений. Отсчёт начинается **после классификации**; длительная
классификация по-прежнему входит в начальные 15 секунд. Для частых запросов
задавайте прямые правила маршрутизации и ограничивайте `classifier.timeout_ms`.
Быстрые локальные ответы и запросы маршрута `yandex` используют прежний тракт.
Переход к LLM после отказа облака не использует этот режим ожидания.

Беззвучный режим проверен на Станции 2 с настоящим ответом после 15 секунд.
Он рассчитан на TTS `audio/opus`; другие кодеки не объединяются. Отмена запроса
останавливает ожидание и передачу тишины. В JSONL-журнале промежуточные сообщения
имеют тип `progress`, поэтому пустые сообщения ожидания не попадают в ответы при поиске истории.

## Модификаторы озвучивания

Модель может менять озвучку своего ответа по просьбе пользователя. Например,
«Спроси нейросеть, пожелай спокойной ночи шёпотом» или «Спроси нейросеть, объяви
отправление поезда с эффектом вокзального громкоговорителя».
Bridge передаёт разметку в штатный синтез Яндекса. Карточка, журнал и контекст
диалога получают текст без разметки. Это работает и для финального ответа
при включённом `local_progress`.

По умолчанию `"llm_tts_markup": true` добавляет описание разметки в системный
промпт подключённой LLM, включая Chat Completions, Responses и ChatGPT.
Чтобы отключить разметку, установите `"llm_tts_markup": false` в `config.json`
и перезапустите Bridge. В этом режиме к синтезатору идёт обычный текст, даже
если модель вернула TTS-разметку.

При включённых `assistant_tools.enabled` и `llm_tts_markup` модель может
вызвать `search_tts_catalog` с коротким названием или ID. Аргумент
`kind: "voice"` ищет голос, а `kind: "audio"` — звук. Например, по запросу
«мяуканье» инструмент вернёт несколько вариантов с точными ID для атрибута
`audio`. Поиск выполняется в каталогах, встроенных в Bridge. В каталог
голосов вошли семь ID, которые вернули озвучку через `TtsGenerate` UniProxy.
Каталог звуков содержит 160 записей из библиотеки Алисы.

| Разметка | Назначение |
| --- | --- |
| `<speaker is_whisper="true">` / `<speaker is_whisper="false">` | Включить или выключить шёпот |
| `<speaker voice="zahar">` | Выбрать голос по ID |
| `<speaker effect="megaphone">` / `<speaker effect="-">` | Включить или снять эффект |
| `<speaker audio="alice-sounds-game-win-1.opus">` | Вставить звук из библиотеки Алисы |
| `<speaker speed="1.2">` | Изменить темп речи, где `1` задаёт обычный темп |
| `<speaker lang="en-US">` | Указать язык синтеза |
| `<speaker voice="zahar" emotion="good">` | Выбрать амплуа для конкретного голоса |
| `sil <[500]>` | Вставить паузу в миллисекундах |
| `зам+ок` | Отметить ударную гласную |
| `транскрипция <[t r a n s k rr ii p c y j schwa]>` | Указать произношение фонемами |

На Станции 2 через Bridge все семь эффектов изменили звучание штатного голоса
с опущенным атрибутом `voice`: `behind_the_wall`, `hamster`, `megaphone`,
`pitch_down`, `psychodelic`, `pulse`, `train_announce`. Например,
`<speaker effect="train_announce">` добавляет эффект к штатному голосу.
Для другого голоса атрибуты можно объединить в одном теге, например
`<speaker voice="zahar" effect="train_announce">`. 
Разметка применяется со следующего фрагмента. Теги пишутся без `</speaker>`.
[Эффекты Алисы](https://yandex.ru/dev/dialogs/alice/doc/ru/speech-effects) ·
[Настройка произношения](https://yandex.ru/dev/dialogs/alice/doc/ru/speech-tuning) ·
[Библиотека звуков](https://yandex.ru/dev/dialogs/alice/doc/ru/sounds) ·
[Голоса и амплуа](https://aistudio.yandex.ru/ru/docs/speechkit/tts/voices)

Атрибут `volume` тоже менял возвращаемый аудиосигнал, но в контрольной фразе
значения `0.2` и `4` дали близкий уровень сигнала. Громкость устройства
управляется отдельно.

## Инструменты локальной LLM

В обработчике `llm` доступны стандартные OpenAI `tool_calls`. Модель выбирает
функцию, сервер выполняет её и отправляет результат модели для окончательного
голосового ответа. Текущее время подготавливается локально перед генерацией;
для явно указанного HTTP/HTTPS URL заранее читается страница, а для вопроса об истории выбираются восемь последних записей
(для «сегодня» — с начала дня в настроенном часовом поясе). Это убирает лишние
обращения к модели и сокращает ожидание на колонке. Модель может уточнить выборку
через `search_history`, если предварительных данных недостаточно. Классификатор маршрутов и планировщик Home Assistant
продолжают использовать обычные completions без этих инструментов.

| Инструмент | Что делает |
| --- | --- |
| `read_webpage` | Читает публичную HTTP/HTTPS страницу по URL, извлекает текст HTML с учётом кодировки или возвращает plain text / JSON. JavaScript не исполняется |
| `search_history` | Ищет запросы колонки и доставленные ответы в текущем JSONL и его сохранённых архивах |
| `current_time` | Возвращает дату, время, день недели и настроенный часовой пояс |
| `check_quasar_bridge_update` | Проверяет последний стабильный релиз Quasar Bridge на GitHub и сравнивает с текущей версией |
| `install_quasar_bridge_update` | Скачивает и проверяет новый релиз, затем запускает обновление самостоятельной установки на колонке |
| `get_quasar_bridge_config` | Показывает каталог голосовых настроек, действующие и сохранённые значения |
| `set_quasar_bridge_config` | Проверяет и атомарно сохраняет несколько настроек с резервной копией |
| `apply_quasar_bridge_config` | Применяет маршрутизацию и журнал либо планирует явно запрошенный перезапуск Bridge |
| `get_quasar_bridge_routing` | Показывает действующие и сохранённые правила, их порядок и версию |
| `set_quasar_bridge_routing_rule` | Создаёт или заменяет одно правило, сохраняет и сразу применяет |
| `control_quasar_bridge_routing_rule` | Включает, отключает, удаляет или перемещает одно правило |
| `test_quasar_bridge_routing` | Проверяет статический маршрут пробной фразы без выполнения команды |
| `get_airplay_status` | Проверяет готовность AirPlay-приёмника, подключение отправителя, воспроизведение и громкость |
| `control_airplay` | Включает или выключает встроенный AirPlay-приёмник |
| `control_airplay_playback` | Управляет воспроизведением подключённого AirPlay-отправителя |
| `set_airplay_volume` | Задаёт громкость AirPlay-аудио в процентах, от 0 до 100 |

Примеры фраз: «Прочитай страницу https://example.org и перескажи», «Найди в
истории, что я спрашивал про свет», «Спроси нейросеть, какая сейчас дата и время».
Первое правило по умолчанию `assistant_readonly` направляет маркеры истории и
чтения URL в LLM **раньше** домашнего правила: фраза «найди в истории запрос
включи свет» должна искать запись, а не повторять действие.

Если ваш `routing.rules` уже задан явно, массив автоматически не дополняется.
Перенесите `assistant_readonly` из нового `config.example.json` в начало своего
массива. Явный префикс «спроси нейросеть» по-прежнему работает для обычных
диалоговых вопросов. Встроенный общий веб-поиск по поисковику не включён (его можно добавить через MCP): `read_webpage`
читает конкретный URL, указанный пользователем или выбранный моделью.

### Конфигурация инструментов

В `config.json`:

```json
"assistant_tools": {
  "enabled": true,
  "web": true,
  "history": true,
  "time": true,
  "play_sound": false,
  "updates": true,
  "configuration": true,
  "timezone": "UTC",
  "max_rounds": 3,
  "max_calls": 4,
  "web_timeout_ms": 8000,
  "web_max_bytes": 1048576,
  "web_max_chars": 12000,
  "history_max_scan_mb": 16
}
```

Выберите свой IANA timezone, например `Europe/Paris`. База часовых поясов
включена в бинарник и доступна на колонке без системного zoneinfo.
`enabled: false` отключает tool-calling целиком; отдельные флаги убирают функции
из списка, доступного модели. Если `assistant_tools` отсутствует, инструменты
выключены для совместимости с API без function calling. Готовый hybrid-пример
включает их; observe- и device-примеры оставляют выключенными до настройки.

Изменение `assistant_tools` требует **перезапуска** процесса: на колонке используйте
`sh /data/opt/quasar-bridge/app/control.sh restart`, для systemd — `systemctl restart quasar-bridge`.
`/healthz` показывает `assistant_tools_enabled`. SIGHUP по-прежнему перечитывает
только `routing` и `conversation_log`; смена пути журнала применяется к поиску
истории сразу. У API LLM должна быть поддержка OpenAI-compatible
`tools`, `tool_choice`, сообщений `tool` и `tool_call_id`.

Один ответ ограничен `max_calls` вызовами, запрошенными моделью, и `max_rounds` раундами; затем модели
остаётся финальный ответ по уже полученным данным. Общий timeout — 65 секунд.
Дополнительно выполняется не более двух быстрых локальных вызовов контекста:
время и чтение явно указанного URL либо релевантная предварительная выборка истории. Они не требуют обращения
к API LLM. Инструменты работают последовательно. После успешного `search_history`
новые сетевые инструменты, включая чтение страниц, звуки, музыку и обновления,
блокируются сервером до завершения приватного разговора, в том числе внутри
одной пачки tool calls: содержимое истории нельзя отправить на сайт через URL.
Если нужны оба источника, модель должна сначала прочитать веб, затем историю. Неизвестные/выключенные функции и неверные
аргументы возвращают ошибку; shell и чтение произвольных локальных файлов
модели не предоставляются. Рабочий лог `assistant_tool` содержит имя, результат
успеха и длительность, без аргументов и содержимого истории/страниц.

### Настройки голосом

При `assistant_tools.enabled: true` управление конфигурацией включено по
умолчанию. Флаг `assistant_tools.configuration: false` отключает все три
инструмента после перезапуска; этот флаг меняется вручную.

Примеры команд:

- «Алиса, какие настройки контекста у квазар бридж?»
- «Алиса, включи журнал диалогов квазар бридж».
- «Алиса, установи время хранения контекста квазар бридж десять минут».
- «Алиса, поменяй часовой пояс квазар бридж на московский».
- «Алиса, перезапусти квазар бридж».

Явное упоминание `Quasar Bridge`, «квазар бридж», «настройки моста» или
«перезапусти мост» направляет административный запрос в LLM, когда эти
инструменты включены, в том числе при собственных правилах маршрутизации.
Модель должна поддерживать вызовы инструментов.

Учитываются варианты названия из распознавания речи: `qwazar bridge`,
`quazar bridge`, «квазар блич» и «квазар брич». После вопроса о Bridge
уточнения «расскажи какие настройки есть», «какие функции сейчас включены»
и «какие у тебя есть утилиты» продолжают эту тему без повторения названия.
Перед ответом подготавливается свежий результат `get_quasar_bridge_config`,
чтобы модель называла фактические настройки и включённые функции.
Новый вопрос о погоде или команда умного дома выбирают свой обычный маршрут.

`get_quasar_bridge_config` принимает необязательный `section`: раздел
(`dialogue_context`, `routing`, `assistant_tools`, `airplay`) или точный путь
(`llm_model`). Без него возвращается весь каталог с описаниями и допустимыми
значениями. `active` показывает действующую конфигурацию, `saved` — значение
из файла (`null`, если поле отсутствует), `effective` — значение с учётом
умолчаний и текущего окружения, `pending` — ожидающие применения изменения.
Настройка с `writable: false` переопределена переменной окружения: изменить её
через файл не получится, поэтому инструмент отклонит такую запись.

Доступны модель и параметры генерации LLM, контекст диалога, ожидание следующего
вопроса, звуковые уведомления, параметры журнала, правила/классификатор/детектор
отказов, часовой пояс и лимиты инструментов, имя/задержка/начальная громкость
AirPlay и отключение функции AirPlay. Сетевые адреса, TLS, ACL, токены, файл
авторизации ChatGPT, настройки MCP-процессов и служебные пути голосом не
читаются и не изменяются. Выбор модели не проверяет её наличие у провайдера.

`set_quasar_bridge_config` принимает объект `changes` с точными путями из каталога:

```json
{"changes":{"dialogue_context.ttl_seconds":600,"assistant_tools.timezone":"Europe/Moscow"}}
```

Весь конфиг проходит ту же проверку, что при запуске. Ошибка хотя бы одного
параметра отменяет пакет целиком. Несвязанные поля сохраняются; прежний файл
попадает в `<config>.voice-backup`, затем новый атомарно заменяет исходный.
Резервная копия содержит конфигурацию до последнего успешного изменения;
при необходимости восстановите её вручную. Запись через симлинк отклоняется.
Инструменты не редактируют `runtime.env`.

Сохранение ещё не означает применение. Если `restart_required: false`, модель
вызывает `apply_quasar_bridge_config` с `{"action":"reload"}`: маршрутизация
и журнал применяются без перезапуска. Если сохранены изменения других разделов,
`reload` отклоняется целиком и сохраняет действующую конфигурацию.

Для остальных настроек скажите «перезапусти квазар бридж» либо сразу явно
попросите применить их с перезапуском. `{"action":"restart"}` доступен только
для штатной standalone-службы на Linux-колонке, запущенной от root: проверяются
раскладка `app/bin`, принадлежность конфига и PID службы. Перезапуск не зависит
от GitHub или номера версии. Отдельный процесс ждёт передачи последнего
аудиофрагмента ответа колонке, выдерживает ещё пять секунд и вызывает штатный
`control.sh restart`. Если соединение оборвалось или TTS не завершился,
ожидание ограничено временем жизни голосового запроса (90 секунд). Результат
записывается в `restart.log`. `status: scheduled` подтверждает планирование,
а успешный запуск проверяется после него через `/healthz` или `control.sh status`.
Для сервера/systemd и ручного запуска используйте обычный способ перезапуска.

### Изменение маршрутизации голосом

Для правил, классификатора и маршрута по умолчанию доступны специальные
инструменты; их включает тот же
флаг `assistant_tools.configuration`. Примеры:

- «Алиса, покажи правила маршрутизации».
- «Алиса, запросы со словами “контрольный апельсин” отправляй нейросети».
- «Алиса, отключи это правило».
- «Алиса, включи правило voice_orange».
- «Алиса, поставь правило voice_orange перед home_devices».
- «Алиса, удали правило voice_orange».
- «Алиса, проверь маршрут для фразы “контрольный апельсин”».
- «Алиса, отключи классификатор и установи маршрут по умолчанию в нейросеть».
- «Алиса, назначь маршрут по умолчанию Алисе, классификатор оставь выключенным».
- «Алиса, включи классификатор».

Фразы о маршрутизации и постоянном направлении запросов в нейросеть/Яндекс
попадают в локальную модель до обычных правил. После просмотра правил можно
продолжить «отключи это правило» без повторения названия Bridge; при
неоднозначном выборе модель должна уточнить, какое правило имеется в виду.

`get_quasar_bridge_routing` возвращает `active`, `saved`, их версии
`active_revision`/`saved_revision` и признак `pending`. Порядок элементов массива
определяет приоритет: выигрывает **первое включённое совпавшее правило**.
Команды управления конфигурацией Bridge остаются доступны независимо от
пользовательских правил.

`set_quasar_bridge_routing_rule` принимает полное `rule` с `name`, `route`,
`match` и необязательным `disabled`. Создание ставит правило первым; замена
правила с тем же именем сохраняет его место. Перед заменой модель читает
правило и сохраняет условия, которые пользователь не просил менять. `before`
задаёт имя правила, перед которым разместить новое/изменяемое; пустая строка
означает конец списка. Другие правила инструмент не переписывает по догадке.

`control_quasar_bridge_routing_rule` принимает точное `name` и `action`:
`enable`, `disable`, `delete`, `move`. Для `move` нужен `before`; для остальных
операций он не используется. Обе операции записи требуют `expected_revision`
из последнего чтения. Если правила изменились параллельно, вызов отклоняется:
модель должна перечитать их и заново подготовить изменение.

Проверка всей конфигурации, резервная копия `<config>.voice-backup` и атомарная
запись используются те же, что у общего инструмента. Правила сразу применяются
к работающему Bridge: `status: applied` не требует дополнительного reload или
перезапуска. Сохранённые изменения LLM, журнала и других разделов при этом не
применяются и не теряются. Если уже есть неприменённые изменения **самого
routing**, сначала явно примените их через reload или отмените; инструмент
редактирования одного правила не активирует их молча.

`test_quasar_bridge_routing` принимает `text` и возвращает статическое решение
для `active`/`saved`: `route`, `rule`, `source`. Инструмент не выполняет команду,
не обращается к LLM-классификатору и не меняет диалоговый контекст. `classify`
означает, что классификатор ещё должен выбрать обработчик. Специальные команды
AirPlay, плеера и диалога обрабатываются отдельно и в этой проверке не
симулируются. Поэтому результат проверки не является подтверждением действия.

`configure_quasar_bridge_routing` принимает актуальную `expected_revision` и
`classifier_enabled` (boolean), `default_route` (`llm`, `yandex`, `home`) или оба
параметра. Сохраняет и сразу применяет изменение без перезапуска. Параметры
независимы: смена маршрута сохраняет состояние классификатора, переключение
классификатора сохраняет выбранный маршрут. `active_behavior`/`saved_behavior`
в результате чтения показывают фактическое состояние, включая старый формат
`default_route: "classify"`.

При выключенном классификаторе запрос без совпавшего правила сразу идёт по
выбранному маршруту. При включённом классификаторе он выбирает обработчика,
а `classifier.on_error` задаёт маршрут при ошибке классификации. Явные правила
сохраняют приоритет; для перенаправления конкретной темы меняйте её правило.
Инструкция, тайм-аут, `on_error` классификатора и настройки детектора отказов
меняются через `set_quasar_bridge_config` с точными `routing.*` путями и reload.

### Проверка и установка обновлений

При `assistant_tools.enabled: true` доступны два инструмента без аргументов:
`check_quasar_bridge_update` и `install_quasar_bridge_update`. Они включены по
умолчанию; `assistant_tools.updates: false` отключает оба после перезапуска.

Примеры запросов:

- «Алиса, проверь обновления» или «Алиса, есть ли обновления?».
- «Алиса, установи обновления».

Правило `bridge_updates` направляет эти короткие команды в LLM до классификатора
и умного дома. Если `routing.rules` задан явно, добавьте это правило из
`config.example.json` в начало списка. Короткая проверка выполняется инструментом
и озвучивает результат без обращения к модели; установка выполняется только
через явный вызов инструмента моделью.

Проверка возвращает текущую и последнюю стабильную версии, наличие обновления,
ссылку на релиз и доступность автоустановки. Используется официальный репозиторий
[skrashevich/quasar-bridge](https://github.com/skrashevich/quasar-bridge/releases).
Если API GitHub недоступен, проверка использует перенаправление официальной
ссылки на последний релиз. Общее ожидание проверки ограничено 8 секундами.
Предварительные релизы и понижение версии исключены. Для сборки с неизвестной
версией (`dev`) сравнение и автоматическая установка недоступны; последняя
версия на GitHub всё равно показывается.

Автоустановка требует Linux ARM64/ARMv7, root и самостоятельной установки с
`app/bin/quasar-bridge`, `VERSION` и PID-файлом текущей службы. Конфигурация должна
принадлежать этой установке. Для YAM, ручного запуска и сервера на другой
платформе инструмент объяснит причину отказа; обновите их вручную.

Инструмент скачивает архив для архитектуры колонки и проверяет SHA-256 до
распаковки. Только после проверки отдельный процесс запускает штатный
`install.sh` с задержкой 5 секунд. Он сохраняет `config.json`, `runtime.env` и
endpoint Алисы, проверяет конфиг перед остановкой, запускает новую версию и
возвращает предыдущую при ошибке запуска. Перезагрузка колонки не нужна;
соединение bridge кратковременно прервётся. Одновременные обновления блокируются.

Результат `scheduled` означает, что установка запланирована. Он **не подтверждает
успех**: после перезапуска повторите проверку версии. Журнал установки находится
в каталоге состояния, по умолчанию `/data/opt/quasar-bridge/update.log`:

```sh
cat /data/opt/quasar-bridge/update.log
sh /data/opt/quasar-bridge/app/control.sh status
```

Инструмент установки вызывается моделью только по явной просьбе пользователя
обновить bridge. Ему нельзя передать URL, команду оболочки или произвольную версию.
После чтения приватной истории оба инструмента блокируются до нового разговора.

### Звуки на колонке

Чтобы дать модели инструмент `play_sound`, включите `assistant_tools.enabled`
и `assistant_tools.play_sound` в `config.json`, затем перезапустите bridge.
По умолчанию воспроизведение выключено.

Инструмент принимает один обязательный аргумент `source`:

- `{"source":"notification"}` — короткий сигнал уведомления;
- `{"source":"success"}`, `{"source":"error"}` или `{"source":"timer"}` —
  сигнал успеха, ошибки или таймера, однократно;
- `{"source":"https://example.org/sound.mp3"}` — аудио по HTTP/HTTPS.
  Для HLS используйте ссылку с расширением `.m3u8`.

Примеры: «Алиса, спроси нейросеть: воспроизведи сигнал уведомления» или
«Алиса, спроси нейросеть: воспроизведи аудио по ссылке …».
Звук запускается на колонке, которая обрабатывает запрос. Ссылка должна быть
доступна самой колонке; поддерживаются и адреса локального медиасервера.
URL с логином, паролем или фрагментом `#…` не принимаются.

На один ответ можно поставить в очередь один звук. Повтор одинакового вызова
не дублирует воспроизведение. Директива отправляется вместе с финальным ответом;
ошибка модели или отмена запроса удаляют её из очереди. Результат `queued`
означает постановку в очередь, а не подтверждение слышимого звука. URL использует
штатный медиаплеер и может заменить текущий трек. Громкость инструмент не меняет.
При воспроизведении URL ответ модели остаётся текстовым: так короткий файл
слышен целиком, без одновременного голосового подтверждения.

При включённых `assistant_tools.web` и `assistant_tools.play_sound` доступен
также `play_music({"source":"https://example.org/music"})`. Он открывает страницу,
находит публичные аудиоссылки в HTML, JSON-LD, данных Next.js-плееров и статических
настройках JavaScript-плеера. Если HTML содержит плеер без аудиоссылки, проверяет
до трёх подключённых скриптов с того же origin (схема, хост и порт); общий лимит
действует и при переходах между страницами. Скрипты и их зависимости не исполняются.
Если треков на странице нет, проверяет до трёх музыкальных разделов того же сайта.
Для полностью динамических плееров без статических аудиоссылок понадобится
прямая ссылка на аудио.

Несколько MP3 играют последовательно через поток bridge; один файл или HLS
передаётся штатному плееру напрямую. Частота, число каналов и битрейт могут
меняться между MP3; каждый файл проверяется по заголовку MPEG Layer III. Ограничения: 64 трека,
64 МиБ на файл, 512 МиБ на очередь, два часа. Произвольная перемотка очереди не поддерживается.

Музыкой, запущенной через `play_music`, можно управлять голосом:

- «Алиса, следующий трек» / «Следующая песня» / «Дальше»;
- «Алиса, предыдущий трек» / «Предыдущая песня» / «Назад»;
- «Алиса, поставь музыку на паузу» / «Пауза»;
- «Алиса, продолжи» / «Сними с паузы»;
- «Алиса, начни песню сначала» / «Сначала»;
- «Алиса, хватит» / «Стоп» / «Останови музыку».

Для собственной очереди команды обрабатываются сразу, без запроса к модели.
Явная команда «Включи музыку с сайта …» с распознанным адресом также вызывает
`play_music` напрямую, если политика маршрутизации выбрала локальный обработчик.
Для запуска с указанной страницы ждать ответ LLM не требуется. Неоднозначные
запросы остаются у модели; адрес не берётся из истории разговора.
Bridge сопоставляет позицию штатного плеера с длительностью MP3-фреймов;
скачивание треков наперёд не меняет выбранную песню. После паузы MP3-поток
начинается с сохранённой позиции с точностью до одного фрейма, без перекодирования.
Первый и последний треки не переключаются по кругу. Управление привязано
к колонке и подтверждённому плеером StreamID; чужое воспроизведение не затрагивается.
Очередь хранится в памяти до двух часов и сбрасывается при перезапуске bridge.

На Станции с HTTP loopback endpoint адрес потока определяется автоматически.
Для отдельного сервера или TLS задайте `assistant_tools.music_base_url`, например
`"https://bridge.example.org:8443"`: этот адрес должен быть доступен колонке и
разрешён её сертификатами и `allowed_ips`. Для публичных страниц и треков
`play_music` сохраняет ограничения веб-чтения на приватные IP и перенаправления.

Фраза «Алиса, включи музыку с сайта example.org/music» направляется в локальную
модель правилом `music_from_site`, которое стоит перед `yandex_services`.
Если в конфиге задан собственный массив `routing.rules`, добавьте это правило
из примера конфига вручную. Адрес можно произнести словами «точка» и «слэш»;
bridge нормализует адрес до обращения к модели, не подменяя домен сайта.

Правило `speaker_playback` ставится первым: «Алиса, хватит», «Стоп», «Останови
музыку» и «Поставь на паузу» передаются штатному обработчику Алисы без обращения
к классификатору или умному дому. Добавьте это правило из примера, если используете
собственный массив правил. Иначе короткое «Хватит» может ошибочно классифицироваться
как команда умного дома.

После чтения приватной истории `play_sound` и `play_music` блокируются до нового разговора,
как и веб-чтение. Диагностика `-query` использует тестовый контекст колонки:
`play_music` и `play_sound` проходят обычную обработку, а команды плееру выводятся
в JSON без отправки колонке. Для запуска звука нужен запрос через Станцию.

### Диагностика музыки с сайта

Проверить команду и поиск аудиоссылок можно без колонки:

```sh
./bin/quasar-bridge -config config.json \
  -query 'Включи музыку с сайта rpfm точка ru'
./bin/quasar-bridge -config config.json \
  -query 'Включи музыку с сайта svk.su'
./bin/quasar-bridge -config config.json \
  -query 'Включи радио по ссылке https://hls.rpfm.ru/rpfm/aac_hifi.m3u8'
```

`-query` проходит маршрутизацию и обработчик с текущими настройками инструментов.
Для музыки нужны `assistant_tools.enabled`, `web` и `play_sound`.
Для аудио результат содержит `playback` — команды плееру и
`playback_simulated: true`. В `playback[].tracks` перечислены исходные аудиоссылки
и названия треков в порядке воспроизведения. Для прямого HLS-потока там одна ссылка.
Поле `playback[].url` содержит адрес, который получил бы плеер: для MP3 это
поток очереди Bridge. URL очереди в таком отчёте относится к временному
диагностическому процессу. Этот результат подтверждает подготовку команды.
При ошибке причина выводится в stderr, процесс завершается с кодом 1.

Проверка использует обычный `play_music`, включая переходы в музыкальные разделы
и ограничения на приватные адреса, DNS и перенаправления. При загрузке страницы
сайт в локальной сети или домен, разрешающийся в приватный IP, будет заблокирован
до HTTP-запроса.

Прямая ссылка с расширением `.m3u8` или аудиофайла возвращается без скачивания:
это проверка распознавания ссылки, а не доступности потока, кодека или слышимого
воспроизведения. HTML-страница с одной ссылкой вида
`<a href="https://hls.rpfm.ru/rpfm/aac_hifi.m3u8">Радио</a>` тоже поддерживается.
Найденный HLS виден в `playback[].url`; при голосовом запросе он передаётся
штатному плееру колонки.
Скрипты плеера не исполняются; наличие кнопки «Слушать» на сайте само по себе
не означает, что в HTML есть аудиоссылка. Например, у `rpfm.ru` тег `<audio>`
пустой, а статический адрес `https://hls.rpfm.ru/rpfm/playlist.m3u8` задан
в отдельном скрипте плеера. Такой вариант тоже распознаётся. Адреса, которые
появляются только после выполнения JavaScript или запроса к API, не вычисляются.

Если колонка отвечает «Не удалось включить музыку с этой страницы», в сервисном
журнале ищите `native_music_failed`: поле `error` содержит причину, `request`
связывает её с `native_route_decision`. Сетевые ошибки различают DNS, приватный
адрес, TLS, таймаут и HTTP-статус. На колонке журнал находится в
`/data/opt/quasar-bridge/service.log`, на сервере доступен через
`journalctl -u quasar-bridge`. Ошибки загрузки страницы не подтверждают сбой LLM.

Чтобы проверить распознанную речь, включите [журнал запросов и ответов](#журнал-запросов-и-ответов)
и найдите событие `transcript` для нужного запроса. Его текст можно передать в
`-query`, чтобы повторить поиск аудио и подготовку команды плееру. Команда
`-route 'Включи музыку с сайта rpfm точка ru'` отдельно показывает маршрут:
`yandex` означает, что запрос не попал в локальный поиск аудио; проверьте
`routing.rules`, `music_from_site` и настройки инструментов.

### История и ограничения веб-чтения

Для накопления истории включите `conversation_log.enabled`. Поиск читает только
файлы из этого настроенного журнала и его `.1`…`.N`, включая записи, оставшиеся
после выключения записи. Функция не восстанавливает уже удалённые архивы.
`query` — слова, которые все должны встретиться в запросе или ответе, без учёта
регистра и различия `е/ё`; пустая строка возвращает последние записи.
`limit` — от 1 до 20, по умолчанию 5; `since` и `until` — необязательные
RFC3339 timestamps, нижняя граница включается, верхняя — нет.

Возвращаются время запроса в настроенном часовом поясе, его текст, доставленный ответ и маршрут. Финальное
ASR объединяется с голосовым запросом; копия `cloud_response` не дублирует ответ.
Текущий незавершённый вопрос исключается; запросы без ответа старше 90 секунд
могут вернуться с пустым ответом. Выдача отсортирована от новых к старым, текст
каждого поля ограничен 1200 символами. История общая для колонок, использующих
один файл журнала; пакет на колонке по умолчанию имеет собственный файл.

`history_max_scan_mb` ограничивает объём чтения, отдавая приоритет новым данным;
при усечении или повреждённых строках результат помечается `partial: true`.
Чтение идёт без блокировки голосового тракта; при одновременной ротации это
best-effort выборка. Содержимое выбранных записей отправляется **вашему API LLM**,
как и сам вопрос, даже если журнал хранится на колонке.

Web reader принимает только публичные HTTP/HTTPS адреса, проверяет DNS и каждое
перенаправление и подключается к проверенному IP. Loopback, частные, link-local
и служебные диапазоны запрещены. Cookies, HTTP-аутентификация и proxy из
окружения не используются. Для маршрута Home Assistant применяется отдельный MCP-клиент, а не
чтение его приватного URL этим инструментом.

Поддерживаются HTML, XHTML, plain text и JSON; объём загрузки, число символов,
redirects и timeout ограничены. Страницы с обязательным JavaScript, логином,
anti-bot защитой или другим типом данных могут быть недоступны. Извлечённые
страницы и старые ответы передаются как данные, а не как системные инструкции.

## Свои MCP-серверы

Диалоговая LLM может использовать инструменты из ваших MCP-серверов, в том числе
без Home Assistant. Поддерживаются **Streamable HTTP**, старый **HTTP+SSE** и
локальные процессы **stdio**. Клиент реализован на официальном
[Go SDK MCP](https://github.com/modelcontextprotocol/go-sdk).

### Пример: поиск через Parallel

Скопируйте [config.mcp.example.json](../config.mcp.example.json), задайте свои `llm_base_url` и `llm_model`,
загрузите `runtime.env` и проверьте подключение:

```sh
cp config.mcp.example.json config.json
set -a
. ./runtime.env
set +a
./bin/quasar-bridge -config config.json -check-config
./bin/quasar-bridge -config config.json -check-mcp
```

В примере включён [Parallel Search MCP](https://docs.parallel.ai/integrations/mcp/search-mcp)
по адресу `https://search.parallel.ai/mcp` с инструментами `web_search` и
`web_fetch`. На момент проверки этот endpoint работает без аккаунта и API-ключа;
у сервиса есть ограничения бесплатного доступа. Подключение к нему не включается
в обычном конфиге автоматически.

Чтобы добавить сервер к существующему конфигу, дополните `assistant_tools`:

```json
{
  "assistant_tools": {
    "enabled": true,
    "mcp_servers": [
      {
        "name": "parallel",
        "transport": "streamable_http",
        "url": "https://search.parallel.ai/mcp",
        "allowed_tools": ["web_search", "web_fetch"],
        "timeout_ms": 20000,
        "max_result_chars": 3000
      }
    ]
  }
}
```

`-check-mcp` выполняет соединение и discovery, показывает имена и количество
доступных инструментов, но **не вызывает их и не обращается к LLM**. При ошибке
сервера возвращает ненулевой exit code. Для проверки полного пути:

```sh
./bin/quasar-bridge -config config.json \
  -query 'Спроси нейросеть: найди в интернете официальную документацию Go по context.WithTimeout'
```

На колонке можно сказать «Алиса, спроси нейросеть: найди официальную документацию
Go по context.WithTimeout». Префикс направляет запрос в локальную LLM. В полном
MCP-примере также добавлено правило для «найди в интернете» и «поищи в интернете».
Для других MCP добавьте свои правила `route: "llm"` или уточните промпт
классификатора. Простое подключение сервера не меняет маршрутизацию музыки,
таймеров и других запросов; правило `home` по-прежнему имеет свою позицию в списке.
Если домашними устройствами должен управлять ваш MCP, поставьте соответствующее
правило `llm` **перед** домашним правилом.

### Авторизация и локальные процессы

Для HTTP/SSE серверов можно задать `url_env` вместо `url`, если адрес содержит
секретный путь, `bearer_token_env` для Bearer-ключа и `headers_env` для других
заголовков. Значения этих полей — **имена переменных окружения**, а не сами секреты:

```json
{
  "name": "private_api",
  "url_env": "CUSTOM_MCP_URL",
  "bearer_token_env": "CUSTOM_MCP_TOKEN",
  "headers_env": {"X-Tenant": "CUSTOM_MCP_TENANT"}
}
```

Переменные задаются в локальном `runtime.env`. Для старого SSE endpoint явно
укажите `"transport": "sse"`. HTTP redirects и переходы SSE на другой origin
не допускаются; указывайте конечный URL. Интерактивные OAuth-входы, sampling и
запросы MCP к пользователю сейчас не поддерживаются.

Для stdio сервер запускается **на том же хосте, где работает Go-прокси**:

```json
{
  "name": "notes",
  "transport": "stdio",
  "command": "python3",
  "args": ["-m", "your_mcp_server"],
  "env": {"MCP_LOG_LEVEL": "warning"},
  "env_from": {"API_KEY": "NOTES_MCP_API_KEY"},
  "allowed_tools": ["list_notes", "create_note"]
}
```

Команда — пример: установите собственный сервер и его runtime самостоятельно.
При запуске Go-прокси на колонке это должны быть доступные на ней программы и
бинарники подходящей архитектуры. Команда вызывается напрямую, без shell;
`args` — отдельные аргументы. `env` содержит обычные значения, `env_from`
переносит выбранные переменные из окружения Go-процесса. Автоматически передаются
только базовые переменные вроде `PATH`, `HOME`, локали и путей CA; ключи LLM и
секреты HA не передаются автоматически. stderr MCP-процесса не
перепечатывается в журнал Go-сервера.

### Выбор инструментов и ограничения

- `name` — уникальное имя сервера: `[a-z][a-z0-9_-]{0,19}`. Модели выдаются имена
  `mcp__ИМЯ__ИНСТРУМЕНТ_ХЕШ`, поэтому одинаковые имена у разных серверов не конфликтуют.
- `allowed_tools` — список исходных имён инструментов MCP; пустой или отсутствующий
  список разрешает все обнаруженные. `denied_tools` исключает инструменты и имеет
  приоритет. `disabled: true` временно отключает сервер.
- Инструменты доступны только обработчику `llm`, в рамках общих `max_rounds` и
  `max_calls`. Они могут менять состояние, если это умеет сервер: подключайте
  доверенные MCP и задавайте нужный список инструментов. Повтор идентичного вызова
  без аннотации `readOnlyHint: true` в одном ответе возвращает сохранённый результат,
  включая ошибку; автоматического повтора после неизвестного исхода нет.
- `timeout_ms` — лимит discovery и каждого вызова (по умолчанию 10000, от 100 до
  60000 мс). `max_result_chars` — ограничение результата для модели (по умолчанию
  12000, от 100 до 20000 символов). Для медленной модели и веб-поиска начните с
  3000. Действует общий лимит LLM-агента 65 секунд; включённый `local_progress`
  сохраняет беззвучное ожидание, но не отменяет этот предел.
- До восьми серверов подключаются параллельно на время **одного локального
  ответа**. Затем соединения закрываются, stdio-процессы завершаются. Каталог
  обновляется на следующем ответе. Поддерживаются до 128 инструментов вместе со
  встроенными, до восьми страниц каталога и до 256 объявленных инструментов на
  сервер; при превышении лимита настройте фильтры или каталог на стороне MCP.
- Ошибка одного сервера не отключает встроенные инструменты и остальные MCP.
  В журнале видны имя сервера, число инструментов, имя вызова, время и исход;
  адреса с секретами, заголовки, аргументы и результаты туда не записываются.
- В модель передаются текст и `structuredContent`. Бинарные изображения/аудио и
  MCP resources/prompts отдельно не предоставляются. Длинный результат обрезается
  с отметкой `truncated`; ошибка инструмента остаётся ошибкой, а не успехом.
- После чтения приватной истории и в следующих связанных репликах MCP-вызовы
  по умолчанию блокируются вместе с внешним веб-чтением. Для конкретного
  доверенного сервера можно явно задать `allow_private_history: true`; это
  разрешит передавать ему данные из истории. К внешнему поиску такое разрешение
  автоматически не добавляется.

Изменение списка серверов, транспорта, фильтров или авторизации требует
**перезапуска Go-сервера**, но не правки кода и не пересборки. На колонке используйте
`sh /data/opt/quasar-bridge/app/control.sh restart`; настройки хранятся в постоянном
каталоге состояния и сохраняются при обновлении пакета. `/healthz` показывает
`mcp_servers_configured` — число настроенных серверов; это не проверка их доступности.

## Правила маршрутизации

Правила задаются в объекте **`routing`** основного `config.json` и меняются
без правки Go-кода и пересборки. Полный пример, повторяющий прежнее поведение,
уже находится в [config.example.json](../config.example.json).

Если `routing` отсутствует, используются встроенные значения по умолчанию.
Указанные поля объекта перекрывают defaults; пропущенные поля сохраняются.
Массив **`rules` заменяется целиком**, а не дополняется. Поэтому для добавления
правила с сохранением прежних скопируйте/измените полный массив из примера.
`"rules": []` отключает быстрые правила, оставляя `default_route`.

В режиме `observe` WebSocket всё равно пересылается в Яндекс: маршрутизация
включается в `hybrid`. Для голоса решение принимается после финального ASR
Яндекса; текстовый запрос удерживается до решения. Пустой ASR идёт в облако
без классификации.

### Формат правил

Ниже — фрагмент пользовательского конфига. В нём явный префикс LLM специально
поставлен раньше домашнего правила:

```json
{
  "routing": {
    "rules": [
      {
        "name": "explicit_llm",
        "route": "llm",
        "match": {"starts_with_any": ["спроси нейросеть", "джарвис,"]}
      },
      {
        "name": "home_lights",
        "route": "home",
        "match": {
          "contains_all_groups": [["свет", "ламп"], ["включ", "выключ"]],
          "contains_none": ["песню", "музыку"]
        }
      },
      {
        "name": "cloud_services",
        "route": "yandex",
        "match": {"contains_any": ["погода", "таймер", "будильник"]}
      }
    ],
    "default_route": "classify",
    "classifier": {"timeout_ms": 8000, "on_error": "yandex"},
    "refusal": {"enabled": true}
  }
}
```

Объедините фрагмент с остальными настройками сервера; это не полный config.
У каждого правила нужны уникальное непустое `name`, `route` из
`home` / `llm` / `yandex` и `match`. **Первое совпавшее правило побеждает**:
приоритет определяется только порядком в массиве. `"disabled": true`
пропускает правило при сопоставлении, но не отменяет проверку его синтаксиса.

Все заданные условия `match` соединяются через **И**:

| Поле | Условие |
| --- | --- |
| `contains_any` | В тексте есть хотя бы одна указанная подстрока |
| `contains_all_groups` | Из **каждой** группы есть хотя бы одна подстрока: группы соединяются через И, элементы группы — через ИЛИ |
| `contains_none` | Ни одной из перечисленных подстрок нет |
| `starts_with_any` | Текст начинается хотя бы с одного указанного префикса |
| `regex` | Совпало регулярное выражение Go/RE2 |

Сопоставление по умолчанию не учитывает регистр. Подстроки не являются целыми
словами; пробелы в обычных правилах значимы. Для границ, альтернатив или
необязательных пробелов можно использовать `regex`, например
`"regex": "^объясни\\s+.+"` в JSON. Регулярные выражения компилируются при
загрузке, не на каждом запросе.

В Go/RE2 граница `\b` определяется по ASCII-классу `[0-9A-Za-z_]`. Поэтому
между «ь» и запятой в «спроси нейросеть, …» такой границы нет. Для русской
фразы явно укажите конец строки (`\z`) или допустимые разделители.
[Синтаксис регулярных выражений Go](https://pkg.go.dev/regexp/syntax#hdr-Syntax)

В этом примере элемента `routing.rules` разделителями служат пробелы, в том
числе неразрывный, и перечисленные знаки препинания.

```json
{
  "name": "my_llm",
  "route": "llm",
  "match": {
    "regex": "^[\\s\\p{Z}]*спроси[\\s\\p{Z}]+нейросеть(?:\\z|[\\s\\p{Z},.!?:;—–])"
  }
}
```

Правило совпадёт с «Спроси нейросеть, что такое квазар» и пропустит
«Спроси нейросетью».

Пустые строки, пустые группы и правило без положительного условия запрещены;
одного `contains_none` недостаточно. Для безусловного выбора используйте
`default_route`. Неизвестные поля и маршруты, одинаковые имена и некорректный
regex отклоняются до применения конфига.

### Если ни одно правило не совпало

`classifier.enabled` явно включает или отключает LLM-классификатор.
При `false` запросы без совпавшего правила идут по `default_route` (`home`,
`llm` или `yandex`); при `true` обработчика выбирает классификатор.

Для совместимости, если `classifier.enabled` отсутствует, поведение определяется
старым `default_route`: `home` / `llm` / `yandex` сразу выбирают обработчика,
`classify` включает классификатор. Если явно выключить классификатор при старом
`default_route: "classify"`, прямой маршрут берётся из `classifier.on_error`.
Голосовой инструмент сохраняет явный переключатель и прямой маршрут вместе.

Параметры `classifier`:

Стандартная инструкция направляет обычные факты, определения, справочные
обзоры, простые вычисления и базовые объяснения в Яндекс. Слова «расскажи»,
«почему», «как» и просьба о подробностях сами по себе не означают сложную задачу.
LLM получает задачи с рассуждением в несколько шагов, сравнением по условиям,
кодом или оригинальным текстом, явные обращения к локальной модели, просьбы
озвучить ответ другим голосом, шёпотом, с эффектом или звуковой вставкой,
веб-инструменты и историю запросов. Штатные команды вроде «скажи шёпотом привет»
направляются в Яндекс. При сомнении выбирается Яндекс. Фактический отказ Алисы
обрабатывается отдельно.
Эта инструкция действует после проверки явных правил `routing.rules`.

| Поле | По умолчанию | Назначение |
| --- | --- | --- |
| `enabled` | Не задан: определяется `default_route` | Явное включение/отключение классификатора; выбранный прямой маршрут сохраняется |
| `prompt` | Русская инструкция из полного примера | Системная инструкция классификатору; ожидается JSON `{"route":"home"}`, `{"route":"llm"}` или `{"route":"yandex"}` |
| `timeout_ms` | `8000` | Время классификации, от 1 до 60000 мс |
| `on_error` | `yandex` | `home`, `llm` или `yandex` при ошибке, тайм-ауте, неверном JSON или неизвестном ответе маршрута |

Например, `"default_route": "yandex"` полностью убирает классификацию для
несовпавших запросов. Обычная генерация ответа LLM и планирование HA при этом
сохраняются для правил `llm` и `home`.

### Правила по умолчанию

Без пользовательских изменений используется такой порядок:

| Приоритет | Условие | Маршрут |
| --- | --- | --- |
| 1. `bridge_updates` | Проверка и установка обновлений Bridge | `llm` |
| 2. `speaker_playback` | Короткие команды остановки, паузы и возобновления воспроизведения | `yandex` |
| 3. `music_from_site` | Запуск музыки или звука с сайта | `llm` |
| 4. `assistant_readonly` | История запросов, чтение URL и страниц | `llm` |
| 5. `tts_whisper` | Штатные команды шёпота, например «скажи шёпотом» или «скажи шёпотом привет» | `yandex` |
| 6. `tts_markup` | Просьба озвучить конкретный ответ шёпотом, другим голосом, с эффектом или звуковой вставкой | `llm` |
| 7. `home_devices` | Домашнее устройство/показатель и слово действия/состояния, кроме музыкальных маркеров | `home` |
| 8. `complex_queries` | Явный запрос к модели или сложная задача | `llm` |
| 9. `yandex_services` | Погода, музыка, таймер, будильник, время | `yandex` |
| Нет совпадений | LLM-классификатор, при ошибке запрос идёт в Яндекс | `classify` |

«Объяви шёпотом отправление поезда» идёт в `llm`, в том числе если в той же
фразе попросить эффект вокзального громкоговорителя. Явное обращение
«спроси нейросеть» сохраняет маршрут `llm`.
Если в своём конфиге вы явно задали `routing.rules` или
`routing.classifier.prompt`, перенесите правила или инструкцию об озвучке
из обновлённого `config.example.json`.

Домашнее правило содержит группы подстрок вроде `свет`, `ламп`, `люстр`,
`розетк`, `штор`, `кондиционер`, `датчик`, `температур`, `влажност` и
`включ`, `выключ`, `открой`, `закрой`, `установ`, `состояни`, `горит`.
Подстроки `песню`, `песни`, `музыку`, `радио`, `трек` исключают совпадение
этого домашнего правила.

Маркеры сложных задач по умолчанию: `спроси нейросеть`, `спроси свою модель`,
`напиши код`, `напиши программу`, `реши задачу`, `проанализируй`,
`сравни варианты`, `объясни подробно`. Полные списки — в конфиге-примере.

| Фраза | При стандартном порядке |
| --- | --- |
| «Выключи свет в кабинете» | `home` |
| «Напиши код сортировки» | `llm` |
| «Спроси нейросеть про погоду» | `llm` |
| «Спроси нейросеть, включи свет» | `home`; переставьте явное правило LLM выше, если нужно другое поведение |
| «Включи песню про свет» | `yandex` |
| «Сколько будет три плюс четыре?» | Решает классификатор |

Это по-прежнему эвристики: стандартная подстрока «температура» может выбрать
`home` и вне домашнего контекста. Теперь её можно убрать/уточнить в JSON.

### Что выполняют обработчики

Если `QUASAR_HOME_MCP_URL` не задан, выбранный маршрут `home` заменяется на
`yandex` до начала локальной обработки и потокового ожидания. Это относится
ко всем правилам, `default_route`, результату классификатора и его `on_error`.
Примеры с `home` выше предполагают подключённый HA.

- `home`: выбор разрешённых устройств, ограниченный план и проверка результата
  в HA. Распознанные шаблоны вопросов о состоянии, например «горит ли свет»,
  используют отдельную ветку без физических действий.
- `llm`: краткий ответ модели; она не получает произвольный доступ к HA.
- `yandex`: разрешение штатного облачного исполнения. Аудио, неизвестные
  сообщения и обычные ответы проходят исходными байтами; для голоса Go управляет
  служебным approval-флагом и Continue/Cancel.

Ошибку HA нельзя превратить в повтор команды в облаке: действие могло уже
выполниться. Поэтому после начала `home` запрос при ошибке не отправляется
в Яндекс, даже если `classifier.on_error` установлен в `yandex`.
`on_error` относится **только к классификации до выбора обработчика**.
Ошибка генерации LLM также даёт локальное сообщение, без облачного повтора.
Отмена или истечение общего контекста (90 секунд) могут прервать озвучивание.

### Переход к LLM после отказа Алисы

`routing.refusal` задаёт дополнительную проверку уже полученного облачного
ответа, независимо от того, как был выбран маршрут `yandex`:

```json
{
  "routing": {
    "refusal": {
      "enabled": true,
      "prefixes": ["я не знаю", "я не поняла", "увы"],
      "contains_any": ["не знаю", "не поняла", "не могу понять"]
    }
  }
}
```

Нужны оба условия: ответ начинается с одного из `prefixes` **и** содержит
одну из фраз `contains_any`. Регистр и повторные пробелы в этой проверке
нормализуются. `"enabled": false` отключает замену отказов. Полные стандартные
формулировки сохранены в [config.example.json](../config.example.json).

Защита от двойного исполнения не настраивается: замена допустима только до
начала облачного аудио и без исполнительных/неизвестных директив.
`client_action:tts_play_placeholder` допустима. Исходный отказ и его аудио
подавляются, LLM получает исходный вопрос, ответ озвучивается через Яндекс TTS.
Если условия не соблюдены, сохраняется штатный ответ Алисы.

### Проверка и применение изменений без перезапуска

Сначала проверьте JSON и выбранный маршрут, загрузив окружение своей установки:

```sh
set -a
. ./runtime.env
set +a
./bin/quasar-bridge -config config.json -check-config
./bin/quasar-bridge -config config.json -route 'Выключи свет в кабинете'
```

`-check-config` валидирует конфигурацию без сетевых вызовов. `-route` не
управляет устройствами, не генерирует ответ и не выполняет запрос в Яндексе,
но может вызвать LLM-классификатор, если правила не совпали. Пример результата:
`{"route":"home","rule":"home_devices","source":"rule"}`.
Другие значения `source`: `default`, `classifier`, `classifier_error`.
В отличие от него, `-query` выполняет выбранный локальный обработчик.
Диагностические флаги нельзя совмещать.

Для systemd:

```sh
sudo systemctl reload quasar-bridge
sudo journalctl -u quasar-bridge -n 20 --no-pager
```

Обновлённый шаблон unit содержит `ExecReload=/bin/kill -HUP $MAINPID`.
Если unit уже был установлен, добавьте эту строку в его `[Service]` (сохранив
свои пути/пользователя) и выполните `sudo systemctl daemon-reload`.
При ручном запуске отправьте `kill -HUP PROCESS_ID`, заменив `PROCESS_ID`
PID работающего Go-процесса.

Успешная отправка сигнала ещё не доказывает применение: в журнале должно
появиться **`routing_reloaded`**. `/healthz` возвращает `routing_revision`
и число активных правил `routing_rules`. При ошибке появляется
`routing_reload_rejected`, а последняя исправная версия остаётся активной.
Сохранять JSON лучше атомарной заменой файла перед сигналом.

Меняются настройки **`routing`** и **`conversation_log`**. Изменение listener, режима, backend URL,
модели, TLS, ACL, `home_warm_area` или `listen_after_reply` при таком reload отклоняется: для них нужен
перезапуск. `runtime.env` также не перечитывается сигналом.
Соединения с колонками не разрываются. Каждый начавшийся выбор маршрута
использует один снимок правил; уже идущая классификация заканчивается по нему,
а следующие выборы и проверки отказов используют новую версию. Начатые действия
не повторяются при reload.

Реализация: [routing.go](../internal/bridge/routing.go),
[engine.go](../internal/bridge/engine.go). Ограничения протокола и проверка
результатов HA сохраняются независимо от пользовательских правил.

## Особенности Home Assistant

Учитываются только сущности с разрешением Assist (`conversation=true`).
Названия областей, friendly name и aliases используются для поиска целей;
состав групп приходит из `member_entity_ids`. Разрешения обнаружения кешируются
на две минуты, перед действием проверяются заново.

План проверяется целиком до исполнения: запрещены неизвестные/недоступные
цели, произвольные сервисы и параметры, дубли и пересечение группы с её
участниками. Максимум четыре действия на запрос. Более 80 разрешённых Assist
кандидатов после отбора по комнате или контекст свыше 24 КБ требуют уточнения.
Инвентарь читается постранично до конца выдачи в пределах времени запроса;
ограничения в 2000 сущностей на домен нет. Неполная выдача, отсутствие прогресса
пагинации и отмена запроса прерывают обработку до планирования действий.

После сервиса читается `ha_get_state`. Для включения/выключения `light`,
`switch`, `fan` проверяется итоговое состояние; для остальных команд
подтверждается только отправка. Список поддержанных сервисов находится в
[`internal/home/controller.go`](../internal/home/controller.go).

LLM может пропустить отдельный светильник при команде для всей комнаты.
Проверка выбранных целей не гарантирует полноту покрытия комнаты. Сверяйте
группы и отдельные устройства. Вопросы о состоянии передают модели указание
не считать настройки Adaptive Lighting источниками света; отдельного
универсального фильтра всех служебных устройств нет.

## Автозапуск на Linux с systemd

Ниже — установка по шаблону для Debian/Ubuntu. Настроенные `config.json`,
`runtime.env` и `private/certs/server.{pem,key}` должны уже существовать.
Бинарник должен быть собран для архитектуры Linux-сервера. Перед
`systemctl enable --now` остановите ручной процесс через Ctrl+C в его терминале.

Если пользователь уже создан, пропустите `useradd`.

```sh
umask 077
sudo useradd --system --user-group --home-dir /opt/quasar-bridge \
  --shell /usr/sbin/nologin quasar-bridge
sudo install -d -m 755 /opt/quasar-bridge
sudo install -d -o root -g quasar-bridge -m 750 /etc/quasar-bridge
sudo install -m 755 bin/quasar-bridge /opt/quasar-bridge/quasar-bridge
```

Для cross-build
в команде `install` используйте имя соответствующего Linux-бинарника.
Удалите или обновите относительные `QUASAR_TLS_CERT`/`QUASAR_TLS_KEY` в `runtime.env`, если
они там заданы: окружение перекрывает абсолютные значения JSON. Относительные
пути считаются от `WorkingDirectory`, а не от расположения `config.json`.
Шаблон unit использует `/opt/quasar-bridge`, `/etc/quasar-bridge` и отдельного
пользователя; при другой установке измените unit или systemd override.


Подготовьте конфиг с абсолютными TLS-путями:

```sh
python3 - <<'PY'
import json
from pathlib import Path

config = json.loads(Path('config.json').read_text())
config['tls_cert'] = '/etc/quasar-bridge/server.pem'
config['tls_key'] = '/etc/quasar-bridge/server.key'
Path('private/config.systemd.json').write_text(json.dumps(config, indent=2) + '\n')
PY
sudo install -o root -g quasar-bridge -m 640 \
  private/config.systemd.json /etc/quasar-bridge/config.json
sudo install -o root -g quasar-bridge -m 640 runtime.env /etc/quasar-bridge/runtime.env
sudo install -o root -g quasar-bridge -m 640 \
  private/certs/server.pem /etc/quasar-bridge/server.pem
sudo install -o root -g quasar-bridge -m 640 \
  private/certs/server.key /etc/quasar-bridge/server.key
sudo install -m 644 scripts/quasar-bridge.service /etc/systemd/system/quasar-bridge.service
sudo systemctl daemon-reload
sudo systemctl enable --now quasar-bridge
sudo systemctl status quasar-bridge --no-pager
```


При реальном пересечении сети контейнеров и адреса LLM проверьте маршрут
командой `ip route get LLM_IP`. Необязательный шаблон
`scripts/quasar-host-route.service.example` берёт назначение, шлюз и интерфейс
из `/etc/quasar-bridge/route.env`; образец — `scripts/route.env.example`.
Основной сервис не включает этот маршрут автоматически.

## Диагностика

```sh
sudo journalctl -u quasar-bridge -n 100 --no-pager
```

| Симптом | Что проверить |
| --- | --- |
| `configuration rejected` | Неизвестные JSON-поля, пару cert/key, формат `allowed_ips`, обязательные настройки `hybrid` и активные env overrides |
| `403 forbidden` от Go | IP клиента в `allowed_ips`, в том числе адрес проверяющей машины |
| TLS error / колонка не подключается | Доверие CA на колонке, SAN и hostname/IP URL, DNS, firewall, порт |
| В журнале нет кадров после речи | Правильность `uniProxyUrl`, QUIC-обход и применение config после перезагрузки |
| `401`/`403` от MCP или неизвестные tools | Полный Secret URL, загруженный `runtime.env`, совместимость набора `ha_*`; OAuth/Bearer для MCP клиент не выполняет |
| `LLM returned HTTP 400` | Точный model ID, базовый URL с `/v1`, поддержку `response_format` и `chat_template_kwargs` вашим API |
| Устройство не находится | Assist exposure, область, friendly name/aliases, состояние `unknown`/`unavailable` |
| Команда прошла частично | Отдельные приборы вне группы, лимит действий, проверка остальных состояний в HA; не повторяйте весь запрос вслепую |
| Долгий ответ | Скорость LLM, классификация, HA и первоначальный обход разрешений; `home_warm_area` сокращает холодное обнаружение |

Маршрут виден в `native_route` (`home`, `llm`, `yandex`), замена отказа —
в `native_fallback`, готовый аудиопоток — в `native_tts_ready`.
`home_warm ready=true` означает завершение подготовки кеша, не действие.
Сервер не записывает тексты запросов, аудио и токены в штатный журнал.

В пилоте ответы HA занимали примерно 10–17 секунд. Внешний клиент может
получить тайм-аут раньше завершения и озвучивания. Это не доказывает, что
физическое действие не произошло: сначала проверьте состояние, затем решайте,
нужен ли повтор. Подробности проверок — [docs/validation.md](../docs/validation.md).

## Откат

В режиме `hybrid` standalone-установка на колонке принимает две прямые
аварийные команды:

- «Алиса, переведи квазар бридж в режим наблюдения» (также принимается `observe`).
  Bridge сохраняет `mode: "observe"` и планирует свой перезапуск после ответа.
  После перезапуска запросы идут в Яндекс через Bridge.
- «Алиса, аварийный откат квазар бридж». Bridge планирует восстановление
  штатного endpoint через `control.sh rollback` и перезагрузку колонки.
  Перезагрузка выполняется только при успешном восстановлении endpoint.

Эти команды обрабатываются до правил маршрутизации и классификатора,
без LLM-запросов, в том числе при `assistant_tools.enabled: false` или
`assistant_tools.configuration: false`. Нужно явно назвать Bridge; вопросы
о команде, цитаты, отрицания и составные команды аварийное действие не запускают.
Ответ подтверждает планирование; успешное применение проверяется после
перезапуска. Служебный помощник ждёт окончания передачи ответа (либо завершения
запроса, не дольше его 90-секундного срока), затем ещё пять секунд для озвучивания.
Распознавание речи и озвучивание по-прежнему используют соединение с Яндексом.

Для `observe` сохраняются `config.json.recovery-backup` и, если файл окружения
уже существовал, `runtime.env.recovery-backup`. В `runtime.env` добавляется
`QUASAR_MODE='observe'`, чтобы прежний override `hybrid` не отменил восстановление.
Для возврата в `hybrid` измените режим в конфиге и этот override, затем
перезапустите службу. Журнал перезапуска — `restart.log`, отката — `recovery.log`
в каталоге данных Bridge.

Голосовое восстановление требует standalone-службу Linux с root и проверенным
владением текущим процессом; для `rollback` нужна сохранённая резервная копия
endpoint. Если Bridge остановлен, работает в `observe`, установлен вручную или
через YAM, используйте SSH. При ошибке планирования Bridge сообщает об этом
без обращения к модели; причину можно найти в журнале службы.

Для быстрого отключения локальной маршрутизации задайте `mode: "observe"`
(либо `QUASAR_MODE=observe`, если используете env override) и перезапустите
Go-сервер. Колонка продолжит работать через него с Яндексом.

Для полного отката сначала восстановите штатную конфигурацию и CA на колонке:

```sh
ssh -p "$SPEAKER_SSH_PORT" "root@$SPEAKER_HOST" \
  "sh '$STAGE/rollback-pilot.sh' && reboot"
```

Убедитесь, что колонка снова подключается штатно. После этого можно остановить
и отключить прокси:

```sh
sudo systemctl disable --now quasar-bridge
```

При нестандартных firmware-путях используйте те же `QUASAR_DEVICE_*`, что при
применении. Если был установлен отдельный host-route unit, его отключение и
удаление конкретного маршрута выполняются отдельно по вашей конфигурации.

## Справочник конфигурации

Переменные окружения имеют приоритет над JSON, в том числе если значение
пустое. Пустые `listen`, `upstream` и `mode` затем получают значения
по умолчанию. JSON-файл всё равно должен существовать. Неизвестные поля отклоняются.

| JSON | Переменная окружения | Значение/назначение |
| --- | --- | --- |
| `listen` | `QUASAR_LISTEN` | Адрес и порт; по умолчанию `localhost:8443` |
| `upstream` | `QUASAR_UPSTREAM` | По умолчанию `wss://uniproxy.alice.yandex.net/uni.ws` |
| `mode` | `QUASAR_MODE` | `observe` по умолчанию, либо `hybrid` |
| `tls_cert` | `QUASAR_TLS_CERT` | Путь к сертификату сервера |
| `tls_key` | `QUASAR_TLS_KEY` | Путь к ключу; задаётся вместе с сертификатом |
| `allowed_ips` | `QUASAR_ALLOWED_IPS` | JSON-массив или список IP через запятую; пустой отключает фильтр |
| `llm_base_url` | `QUASAR_LLM_BASE_URL` | Базовый API URL с `/v1` |
| `llm_model` | `QUASAR_LLM_MODEL` | Идентификатор модели |
| `llm_api` | `QUASAR_LLM_API` | `chat_completions` по умолчанию, `responses` либо `chatgpt` для подписки; пустое значение выбирает `chat_completions` |
| `llm_chatgpt_auth_file` | `QUASAR_LLM_CHATGPT_AUTH_FILE` | Защищённый файл регистрации и OAuth-токенов ChatGPT; на колонке задайте постоянный путь в `/data` |
| `llm_chat_parameters` | — | Явные параметры Chat Completions; `null` удаляет поле из запроса. По умолчанию пусто; требуется перезапуск |
| `llm_tts_markup` | — | Описание и применение TTS-разметки в ответах LLM, по умолчанию `true`. Требуется перезапуск |
| `llm_reasoning_effort` | `QUASAR_LLM_REASONING_EFFORT` | Необязательный effort для Responses/ChatGPT; допустимые значения зависят от модели |
| `llm_max_output_tokens` | — | Положительный бюджет Responses с учётом reasoning, по умолчанию 4096; в `chatgpt` не отправляется |
| `llm_hosted_tools` | — | `web_search` и/или `code_interpreter` для Responses, только `web_search` для `chatgpt`; по умолчанию пуст |
| `home_warm_area` | `QUASAR_HOME_WARM_AREA` | Подготовка кеша света/выключателей области, не область по умолчанию |
| `dialogue_context` | — | Короткая память локального диалога; по умолчанию включена, требуется перезапуск |
| `local_progress` | — | Потоковое ожидание долгих локальных ответов; по умолчанию выключено, требуется перезапуск |
| `listen_after_reply` | — | Снова слушать после локального голосового ответа; по умолчанию `true`, `false` завершает диалог; требуется перезапуск |
| `assistant_tools` | — | Инструменты диалоговой LLM, лимиты и часовой пояс; требуется перезапуск |
| `conversation_log` | — | Настройки JSONL-журнала; перечитывается по `SIGHUP`, по умолчанию выключен |
| `routing` | — | Правила, классификатор и детектор отказов; перечитывается по `SIGHUP` |
| — | `QUASAR_HOME_MCP_URL` | Необязательный URL HA MCP; пустой отключает HA и передаёт домашние запросы в Яндекс |
| — | `QUASAR_LLM_API_KEY` | Необязательный Bearer-ключ LLM |

Если оба TLS-поля пусты, сервер работает по HTTP/WS. Примеры подключения
колонки на отдельный хост выше предполагают TLS; для них нужен именно WSS endpoint и доверие CA.

## AirPlay

Поддерживаются два аудиорежима: буферизованный AAC-LC по TCP (стерео,
44100/48000 Гц, тип потока 103) и realtime ALAC по UDP (S16 стерео,
44100 Гц, 352 сэмпла, тип потока 96). Realtime нужен, в частности, для
проверенного сценария Яндекс Музыки с iPhone; Apple Music в той же проверке
использовала буферизованный AAC. Оба декодера написаны на Go, CGO не требуется.
В realtime-режиме звук обычно отстаёт примерно на две секунды. Если при паузе
отправитель прекращает передачу без FLUSH, уже принятый звук доигрывает.

В режиме `hybrid` встроенный приёмник доступен по явной команде:
«Алиса, включи эйрплей», «Алиса, выключи эйрплей»,
«Алиса, статус эйрплей». Пока подключён AirPlay-отправитель,
«пауза», «продолжи музыку», «стоп», «следующий трек», «предыдущий трек»,
«начни трек сначала», «громче» и «тише» относятся к нему.
`Стоп` останавливает воспроизведение, а `выключи эйрплей` — сам приёмник.
Смена трека и другие удалённые команды зависят от возможностей отправителя;
ошибка не выдаётся за выполненное действие. Когда отправитель не подключён,
обычные медиакоманды сохраняют прежний маршрут.

Поддерживаются также `enable airplay`,
`disable airplay`, `airplay status`. Команды распознаются до правил
маршрутизации, музыки, Home Assistant и классификатора LLM; доступность
модели и `assistant_tools.enabled` на них не влияют. Прямой обработчик принимает
только отдельную команду целиком: вопросы вроде «как включить AirPlay»,
отрицания и составные запросы проходят обычную маршрутизацию.
Если запрос попал в LLM с включёнными инструментами, она может управлять
AirPlay по явной просьбе пользователя. В режиме `observe` запросы идут в Яндекс как обычно.

Bridge создаёт один приёмник на процесс. До команды включения он не открывает
AirPlay/mDNS-сокеты, не создаёт pairing-файлы и не запускает PCM-проигрыватель.
«Выключи эйрплей» останавливает только этот приёмник; Bridge и штатные
службы колонки продолжают работать. При нормальном завершении Bridge
приёмник закрывается; после перезапуска снова выключен. Ответ «включён»
означает готовность принимать подключения, а не наличие воспроизводимого аудио.
После успешного запуска приёмника ответ содержит `should_listen: false`,
независимо от `listen_after_reply`. Это относится и к прямой команде,
и к запуску через `control_airplay`: подтверждение озвучивается, затем колонка
завершает ожидание следующей команды. Правило действует только для запроса,
запустившего AirPlay.

Необязательные настройки в `config.json`:

```json
"airplay": {
  "disabled": false,
  "name": "My Station AirPlay",
  "listen_address": ":7000",
  "data_dir": "/data/opt/quasar-bridge/airplay"
}
```

| Поле | Значение |
| --- | --- |
| `disabled` | `false`: команды доступны по запросу; `true`: встроенный приёмник полностью отключён |
| `name` | Имя в списке AirPlay; без значения используется имя из `station-airplay` |
| `interface` | Имя сетевого интерфейса для mDNS; пустое — выбор библиотеки |
| `listen_address` | Адрес TCP-приёмника; без значения `:7000` |
| `data_dir` | Приватные pairing-ключи/идентификатор; по умолчанию `$QUASAR_DATA_DIR/airplay` или `/data/opt/quasar-bridge/airplay` |
| `aplay` | Необязательный внешний проигрыватель; без значения используется PCM-модуль, встроенный в бинарник Bridge |
| `device` | ALSA PCM-устройство; без значения используется выбор библиотеки |
| `output_delay_ms` | Необязательная задержка вывода 0–5000 мс; отсутствие сохраняет настройку библиотеки |
| `initial_volume_db` | Необязательная начальная громкость в децибелах; отсутствие сохраняет настройку библиотеки |

Громкость можно задать голосом: «громкость 5» использует шкалу 0–10
и означает 50%; «громкость 35 процентов» или «громкость 35%» — шкалу 0–100.
Это громкость AirPlay-аудио; системный ALSA-микшер не меняется.
Фразы с явной целью вроде «сделай телевизор тише» остаются обычными запросами.

### Инструменты AirPlay для LLM

В режиме `hybrid`, при `assistant_tools.enabled: true` и `airplay.disabled: false`,
модель получает четыре встроенных инструмента. Они используют тот же приёмник,
что и прямые голосовые команды; отдельный экземпляр не запускается.
Дополнительный флаг в `assistant_tools` не нужен. При отключённом AirPlay или
в режиме `observe` эти инструменты не публикуются.

| Вызов | Назначение |
| --- | --- |
| `get_airplay_status({})` | Текущее состояние: `enabled`, `state`, `name`, `connected`, `playing`, `volume_db` и ошибка при её наличии |
| `control_airplay({"action":"start"})` | Запустить приёмник; `stop` выключает его и завершает подключение |
| `control_airplay_playback({"action":"pause"})` | Также доступны `resume`, `stop`, `next`, `previous`, `restart`, `volume_up`, `volume_down` |
| `set_airplay_volume({"volume":35})` | Установить 35%; допустимы целые значения 0–100, 0 означает тишину |

Например: «Спроси нейросеть, подключён ли сейчас кто-нибудь по AirPlay»,
«Попроси нейросеть поставить AirPlay на паузу» или
«Спроси нейросеть, установи громкость AirPlay на 35 процентов».
LLM получает инструкции различать включённый приёмник, подключённого
отправителя и воспроизведение: `running` само по себе не означает, что играет музыка.
После управляющего вызова инструмент возвращает сообщение и актуальное состояние.

Управление воспроизведением и громкостью требует подключённого отправителя.
Переключение треков зависит от его поддержки удалённых команд; ошибка
возвращается модели и не считается успехом. Действие `stop` в инструменте
воспроизведения оставляет приёмник включённым, а в `control_airplay` выключает его.
Модель не выбирает музыку на телефоне и не подключает телефон сама:
пользователь выбирает колонку в списке AirPlay на устройстве-отправителе.
Инструменты не вызываются автоматически при старте Bridge.

### Требования и диагностика AirPlay

Изменение этих настроек требует перезапуска, SIGHUP их не применяет.
Нужны штатная `libasound.so.2`, её ALSA-конфигурация/плагины, доступ к аудиоустройству,
свободный TCP-порт и mDNS в локальной сети. Системный `aplay` не используется.
Библиотека `station-airplay` выбирает встроенный 32- или 64-битный PCM-модуль
по ELF-архитектуре ALSA, независимо от архитектуры Bridge и ядра.
Пользователь устанавливает только `quasar-bridge`; при включении AirPlay нужный
модуль автоматически извлекается в приватный кэш `<data_dir>/pcm/`.
Содержимое кэша проверяется по SHA-256 и восстанавливается при повреждении.
Отдельных исполняемых файлов рядом с Bridge не требуется. Стандартные загрузчики
glibc (`ld-linux-armhf.so.3` или `ld-linux-aarch64.so.1`) должны быть доступны.
Этот проигрыватель предназначен для Linux с ALSA/glibc; окружение только
Android/bionic без этих библиотек требует другого аудиобэкенда.

Перед включением встроенного приёмника Bridge проверяет загрузку библиотеки и
наличие нужных ALSA-функций. Проверка не открывает PCM и не воспроизводит звук;
конструкторы штатной библиотеки могут инициализировать своё служебное состояние.
Проверка не подтверждает реальное звучание динамика. Сам проигрыватель
открывает выбранный `device` при поступлении аудио и использует штатную цепочку
ALSA для микширования с Алисой, изменения частоты и числа аппаратных каналов.
Он не меняет системную громкость или ALSA-конфиги.

Если в журнале указана отсутствующая библиотека или загрузчик,
проверьте окружение колонки. Ошибка об отсутствующем встроенном PCM означает,
что использована незавершённая разработческая сборка: сборщик speaker-пакета
и команды из `REBUILD.md` автоматически создают законченный одиночный бинарник.
Обычный `go build` компилирует основной код; следующий шаг сборки встраивает PCM.
При обновлении установленного Bridge можно заменить только его бинарник —
скрипты, конфиги и дополнительный проигрыватель для этого обновлять не требуется.
Пользовательский проигрыватель получает прежние аргументы
`-q -D DEVICE -t raw -f S16_LE -c 2 -r RATE`; встроенная проверка `--check`
к такому переопределению не применяется. Для устройства отправителя колонка должна быть достижима
в той же локальной сети; правила доступа к HTTP Bridge не ограничивают
сам AirPlay-приёмник.

Если установлен отдельный `station-airplay`, остановите его штатной командой
и отключите его автозапуск до включения встроенного приёмника.
Для сохранения существующей AirPlay-идентичности задайте
`"data_dir": "/data/opt/station-airplay/state"` (либо фактический старый каталог).
Не запускайте оба экземпляра с одним каталогом состояния одновременно.
Не удаляйте pairing-каталог при обновлении.

### Журнал AirPlay в браузере

Встроенная страница `/diagnostics/` показывает состояние AirPlay и сообщения
Bridge с запуска процесса, до 1 МиБ. Можно приостановить обновление страницы
и скачать журнал в `.txt`; запись событий Bridge при этом продолжается.
Статус воспроизведения сам по себе не подтверждает наличие слышимого звука.

Откройте SSH-туннель с компьютера к колонке и оставьте соединение работающим:

```sh
ssh -p 2222 -N -L 127.0.0.1:18443:127.0.0.1:8443 root@SPEAKER_IP
```

Затем откройте [страницу диагностики](http://127.0.0.1:18443/diagnostics/).
Для другого SSH-порта или HTTP-порта Bridge измените соответствующее значение
в команде. Страница доступна только через localhost, поэтому прямой запрос
по сетевому адресу колонки будет отклонён.

Для разбора проблемы включите AirPlay, повторите сбой и скачайте журнал сразу
после него. Укажите модель колонки, приложение и версию iOS. В диагностике RTSP
видны сформированные коды ответов и параметры SETUP; ключи и тела pairing-запросов
этими строками не выводятся. Полный сервисный журнал остаётся в `service.log`.

### Проверка AirPlay командами

```sh
quasar-bridge -config config.json -check-config
quasar-bridge -config config.json -route 'Алиса, включи эйрплей'
quasar-bridge -config config.json -query 'статус эйрплей'
```

Маршрут должен быть `{"route":"airplay","source":"airplay"}`.
`-route` только объясняет маршрут. `-query` исполняет команду в отдельном
временном процессе: включение с этим флагом заканчивается выключением
при выходе процесса и не меняет уже запущенный Bridge. Для управления
постоянным экземпляром используйте голосовой запрос.

`GET /healthz` содержит объект `airplay` с полями `enabled`, `state`,
`name`, `address`, `error`, `connected`, `playing`, `volume_db`; состояние `running` означает готовность
приёмника к подключениям. При отключённой функции или `observe` возвращаются
`enabled: false`, `state: "stopped"`. Ошибка AirPlay остаётся отдельной
ошибкой и не отправляет исходную команду в LLM или Яндекс повторно.

Локальные тесты проверяют маршрутизацию, отказ при старте, состояние,
пассивный конструктор и независимость приёмника от контекста голосового
запроса. Это не заменяет проверку реального голосового ввода и воспроизведения
с AirPlay-отправителя на конкретной колонке.
